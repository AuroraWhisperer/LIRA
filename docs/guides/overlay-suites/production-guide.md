# 如何制作一套完整的直播视觉主题

本文把「月渡花汀」的经验整理为后续制作建议，章节顺序便于执行，并非当时对话的逐步重放。实际发生的试做、否定、纠正与认可见 [调试复盘](iteration-history.md)；当前状态见 [入口](README.md)，文件出处见 [来源索引](sources-and-history.md)。

## 1. 先整理已知的风格和用途

把已确认的用途、参考和画风写成一份简短需求卡，尚未确定的部分留待样片比较。下表按月渡花汀最终版本回填，包含后来才出现的纸伞和 2K 目标，并非最初需求原文：

```yaml
主题名: 月渡花汀
视觉主线: 银蓝折扇、月色山水、白山茶；感谢扩展为山水纸伞和花汀
画法: 工笔细线、矿物水彩、水墨与绢纸质感
主色: 月白、雾蓝、银蓝、靛青；极少量淡金
背景密度: 中等；远景低对比，前景只保留必要装饰
主体留白: 为直播主体、昵称、信息和组件搭配留空间
组件: 静态/动态背景、弹幕、礼物许愿、时钟、全屏感谢、开播
目标画布: 2560×1440（已确认的动态背景输出；其他部件按各自契约）
动态信息: 昵称、头像、身份、礼物、数量、金额、进度、时间、SC
参考用途: 视频看结构和时间顺序；开播成品看配色和材质
禁止项: 不加入人物模型；不把姓名、计数或时间烘焙进装饰图
```

月渡花汀最初图像提示词使用 `#F3F5FA`、`#DDE5F3`、`#8FA9D0`、`#627AA9`、`#253353`。这些色值只是美术风格的参考基准，不要求所有画面和组件严格照搬同一套色板。大面积背景要比装饰和文字淡；身份色允许舰长霁蓝、提督藕紫、总督胭脂红。

先做一张 16:9 概念图，核对画风、密度、留白及核心物件。概念图只能证明方向，不能证明已经有动画。月渡花汀曾从过空改成过满，最终收敛到中等密度；不要把最后生成的最繁密原画直接认作最终构图。

已经有认可版本时，以它作为下一轮基线。先说明这次改哪几个问题、保留哪些部分；拿不准密度、颜色或节奏时，用已有版本作对比。若反馈改变了结构或动作顺序，应同步更新需求卡与预览，不能继续按被否定的方案制作。

## 2. 把整图拆成可以制作和运动的部件

| 部件 | 美术素材 | 程序或实时内容 |
| --- | --- | --- |
| 背景 | 无运动物体的完整底景、月亮、柳叶、灯笼、雾、花瓣 | 枝节摆动、逐叶跟随、水纹、倒影、循环合成或视频播放 |
| 开播 | 折扇、山水、四组花枝、鸟身与两翼、流苏、标题 | 扇片开合、绢带形变、飞鸟、文字、15 秒时间线 |
| 时钟 | 复用折扇、白山茶、流苏、裁切的圆形山水 | 本地时间、日期、秒数、12/24 小时、深浅交替 |
| 弹幕 | 笔刷遮罩、纸面/滚轴、花枝、上任山水、原有身份徽章 | 头像、昵称、正文/表情、礼物/金额、SC、消息队列 |
| 礼物许愿 | 贴圆花饰、横向水墨底、折扇起点 | 礼物图标、名称、已收/目标、进度填充、移动端点 |
| 全屏感谢 | 左右山水纸伞、底部花汀、四角花枝、字体 | 上任/收礼数据、入退场、花瓣、水纹、透明输出 |

每张原画只承担一个明确职责。花枝图集的各组之间留透明间隔；飞鸟身体和两翼分开；需要开合的扇面必须正面、共轴、轮廓完整。月亮将来要消失，就不要把它同时画死在背景里。

图像工具负责生成绘画素材，CSS、Canvas 或离线合成负责动作。月渡花汀使用过 LiraHub `gpt-image-2.5-flare`；这是历史制作记录，不表示新环境一定提供同名工具。复用素材通常不需要再调用图像生成。

## 3. 保留原图，清理透明边缘，再做适配

1. 原始 PNG、完整提示词、模型记录放到本轮 `tmp/<主题>-<部件>/source/`，不要只保留压缩后的 WebP。
2. 裁切透明空白和图集，记录尺寸、坐标、锚点；保留羽毛、花瓣、柳叶边缘的半透明过渡。
3. 在深、浅底色检查白边、杂点、绿边和孔洞。早期开播有绿幕原画，须按当时抠图脚本处理；新生成优先要求真实透明背景。
4. 保存运行时 WebP 及其伴随的来源元数据文件（`.json`）；需要继续精修的图保留无损版本。
5. 用真实显示尺寸看线条和文字，不只看放大的原画。礼物许愿已有 416px / 720px 验收记录，时钟已有小尺寸与双底色记录，可作为同类修改的起点。

降低锯齿不能只把录屏放大。当前动态背景保留原尺寸叶片和柔和的透明边缘，用 3840×2160 合成缓冲后缩到 2560×1440，RGBA 原始帧分别编码，避免 JPEG 中间帧。其山水原画仍只有 1672×941；成片为 2K 不等于原画具有原生 4K 细节。

## 4. 各部件怎样做

> 下文聚焦各部件的设计要点、避坑结论与源码入口；月渡花汀逐毫秒的时间线与可直接复用的制作指令见[可复制提示词](prompts.md)。

### 静态与动态背景

静态版来自 `tmp/opening-moon-fan/source/landscape-v2.png`，通过 `tmp/moonlit-background/grade.py` 调成浅银蓝，压低浓重原色以衬托前景组件。

动态背景采用「干净底景 + 分离素材 + 独立动作 + 合成成片」：底景去掉月亮、悬挂柳枝、前景灯笼、落花和固定水纹，各元素独立运动并在 24 秒（60fps，1440 帧）处首尾闭合（检查 0 秒与 24 秒状态，不重复编码末帧）。当前产品输出为 2560×1440 VP9 WebM（MP4 仅作观看）；六层透明循环属于早期 1080p 合成阶段的调节材料，不能标成六层原生 2K 成片。

之前已明确否定了「只扭曲旧图」和「动幅小到几乎看不见」的做法：在保持固定机位和浅淡画风的前提下，必须做出一眼能看清的独立元素运动。

实现中还要沿用视频延迟加载、静态回退、页面隐藏暂停、销毁释放和系统减弱动态效果模式。当前正式播放入口是 [background-moonlit.js](../../../public/js/overlays/background-moonlit.js)，旧 30fps Canvas 背景不再是最终方案。

### 开播动画

先形成「开扇 → 文案显现 → 停留 → 文案消失 → 收扇 → 留景」的完整循环（月渡花汀最终版约 15 秒，各段节奏见[提示词 D 节](prompts.md#d-开播扇花鹤与时间线)）。

当前是 22 片共轴扇面（早期提示词里的“二十片”只是原画结构要求）。Canvas 绘制和时间线统一放在 [opening-moon-fan-art.js](../../../public/js/overlays/opening-moon-fan-art.js)，加载、暂停与销毁由同目录的 `opening-moon-fan.js` 负责，不要另起第二条动画循环。默认书法标题可用图片，自定义标题和副标题继续保持可编辑；预览无声不代表产品不支持原有音乐设置。

### 时钟

复用开播的扇、花、流苏和山水，重新构图成圆形读数区、外围透明（不照抄参考图中用途不明的三个圆圈）。时钟必须是实时 DOM 文本，只有装饰用图片。

提供浅色底深字、深色底月白字两版，支持固定浅色、固定深色和自动交替（默认 30 秒），保留日期、秒数和 12/24 小时设置。切换配色只改外观，不能把时间做成预渲染数字或另开计时来源。

### 弹幕、消息内上任、礼物与 SC

动作顺序与身份规则以最后确认版本和当前 CSS 为准（精确时长见[提示词 F 节](prompts.md#f-弹幕身份与先后顺序写清楚)）：

- 普通消息先保留对应身份的**小深色底框**，停顿约 0.5 秒后再从左向右刷入墨色；普通观众灰、舰长蓝、提督紫、总督红，身份图标复用项目现有 B 站图片，不自行重画。
- 礼物与 SC 先从**右向左**展开素纸与内容（展开到哪里才显示到哪里），纸面展开后再从**左向右**刷入边饰、笔刷和花枝；消息内上任先自上而下显现背景与头像，再从左向右显现称谓与三只鸟。
- 礼物显示头像、昵称、礼物名、数量和价值，SC 显示完整留言；长文本由布局自然延展，花饰保持固定尺寸不能被拉伸。连续来消息时平滑滚动，不要靠重复建节点制造动效。

「礼物无头像」只适用于全屏感谢样片，不能套用到弹幕里。卷轴淡山水暗纹和绢面微光目前仍是提案预览，未进入已接入的 v6 规则。

### 礼物许愿

最终 v4 采用古风白山茶、墨蓝枝叶、如意云纹和绢带贴圆环绕（避开稀疏的小花冠），圆框紧凑、横向墨条拉长，确保白色名称和计数始终落在深底上。

起点固定银蓝折扇（0 进度也显示），移动端点在 0 进度时隐藏；超额时如实显示计数、进度条视觉封顶，收礼更新复用同一张卡片平滑推进，不重启动效，沿用现有礼物许愿数据链路。

### 全屏上任 / 礼物感谢

采用最新「月伞花汀」样片：两侧大幅斜置山水油纸伞、底部贯穿月色花汀、四角花枝、中央透明（已放弃旧版玉饰第一层、两侧架子和侧边绢带）。上任显示 `new member`、头像、昵称及去掉「新」字的称谓（文楷错落排版 + 宋体昵称）；礼物显示 `new presents`、昵称、礼物名和数量，不显示送礼人头像；单次 9.6 秒完整入退场节奏见[提示词 H 节](prompts.md#h-全屏感谢以最新月伞花汀为准)。

MP4 的深蓝底只是观看背景，透明交付以交互 HTML 和透明 PNG 为准；当前最终月伞版尚未产出已归档的透明 WebM，切勿拿旧版透明视频顶替。当前仍是演示样片，后续接入真实事件属于单独的开发任务，需另行确认礼物队列、触发门槛、配置、头像和生命周期规则。

## 5. 先看完整组合，再接入产品

每个部件交付“美术静帧 + 可播放完整样片 + 可编辑源素材”。月渡花汀的感谢和动态背景都曾因只展示局部或未展示完整组合而被要求重新交付；因此，全屏感谢要一次看到上方英文、左右装饰和下方信息，动态背景要交合成后的完整画面。

接入产品前，先查清该组件对应的归属模块、样式注册表、渲染器和预览链路。在套装清单 `lira-pack.json` 的 `styles` 数组中，资源型成员用 `type` 指定组件类型，用 `preset` 指定预设，并在 `resources` 中列出所需素材。例如，月渡花汀点歌板的 `type` 是 `queue`，`preset` 是 `moonlit-queue`。套装是组件分类入口；各部件保留自己的数据与参数。

静态方向 → 完整动效 → 产品预览 → 持久化/输出，验证随实际改动选择。美术微调不自动扩大为全仓验证；新增枚举、生命周期或跨端协议变更则需要相关契约检查。

## 6. 验收和归档

| 本次改动 | 最有用的证据 |
| --- | --- |
| 原图/透明边缘 | 真实显示尺寸、深浅底的静帧，必要时核对透明通道 |
| 循环/入退场 | 完整播放至少一轮并跨越接头，记录开始、中段、结束 |
| 时钟/进度/消息 | 真实的组件渲染器与测试数据；更新后无重复节点和重复监听 |
| 产品接入 | 添加、保存、重开、输出；涉及桌面特权能力时用 Electron 正常授权路径 |
| 分辨率/编码 | 实际解码尺寸和帧率；素材源分辨率、合成缓冲、输出尺寸分别记录 |

OBS 和哔哩哔哩直播姬都是直播软件，B 站是直播平台。浏览器源测试只覆盖直播画面本身，不能代替 Electron 桌面端预加载和 IPC 的验证。报告写清楚实际检查过什么，未实播就保留未实播说明。

归档至少应包含：需求卡、参考图、原始提示词、原始图、裁切/处理脚本、动作源码、字体许可、完整样片、关键检查结果、版本状态、原路径及校验值。进行新一轮制作时，在 `tmp/` 工作；阶段结束后建立新的日期快照，避免覆盖已确认版本。具体目录约定见[归档说明](../../../archive/moonlit-suite/README.md)。
