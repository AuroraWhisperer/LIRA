# LIRA 客户端架构与命名审查提示词

日期：2026-10-28\
用途：以新下载项目的维护者视角，只读审查当前客户端工作树。审查架构归属与命名是否准确、一致、可理解，不实施整改。

同日复核补充：下述规则已校准，区分事实存在、问题成立和是否值得整改；不保留预设问题数或严重度分布。

## 任务

请审查当前 LIRA 客户端项目，回答两个核心问题：

1. 一个新维护者下载项目后，能否从入口、目录、文档和依赖关系正确理解进程边界、组合根、领域归属、数据所有权及前端页面组织？
2. 目录、文件、类、函数、变量、参数和导出名称是否准确表达实际职责；是否存在会误导维护者、造成错误修改或误认公共契约的名称？

输出一份中文 Markdown 报告。要求细节充分、覆盖主要区域，但只报告有代码或文档证据的问题，不追求问题数量，不进行风格清洗或泛化重构。

## 审查基线与事实优先级

先阅读根 `AGENTS.md`、触及目录的 scoped `AGENTS.md`、`docs/README.md`、`docs/architecture/README.md`、`docs/reference/README.md` 和相关 owner 文档。审查当前完整工作树，包括未提交及非忽略未跟踪源码，不只看 HEAD 或当前 diff；保留所有已有改动，不回退、整理或覆盖。按以下优先级判断“应该怎样”：

1. 当前明确需求；
2. Accepted 规格；
3. Accepted ADR；
4. owning 架构/契约文档；
5. 测试与运行时证据；
6. 现有实现。

代码和通过的测试说明现状，不自动证明名称或架构合理。历史报告只用于定位，结论必须重新对照当前代码。

本项目是 **Electron 桌面为主的本地优先模块化单体**：Electron main 同进程运行本地 Node HTTP/WS 与领域服务，Renderer 使用原生 JavaScript ES modules 和 CSS，OBS 与哔哩哔哩直播姬通过浏览器源消费 overlay。不得把“没有微服务、没有前端框架、没有构建步骤、存在本地服务器、main 文件负责接线”本身列为缺陷。

## 范围与排除项

### 必查范围

- 根入口与项目导航：`package.json`、README、`src/server.js`、`src/electron/entry.js`、`src/electron/main.js`、前端入口。
- 后端与领域：`src/server/`、`src/music/`、`src/bilibili/`、`src/overtime/`、`src/ai/`、`src/games/` 及实际相关的其他领域目录。
- 基础设施：`src/storage/`、`src/shared/`、Electron 适配器、原生助手接线及 `native/audio-assistant/` 的主要类与数据方向。
- 前端：`public/js/admin/`、`public/js/overlays/`、`public/js/playback/`、`public/js/shared/`、其他页面模块，以及 `public/pages/` 与必要 CSS 组织。
- 下载、安装与源码包视角：构建包含/排除规则、源码与运行时/生成物的区分；只审查配置，不读取真实用户数据或秘密。
- 跨层术语：同名是否同义、近似名是否可区分，平台（Bilibili）、直播软件（OBS / Livehime）、客户端、本地服务器、LIRA Server、房间与主播身份是否被混淆。
- 代表性实现细节：每个主要区域都要从文件/目录命名深入到导出、公共工厂、核心状态和关键函数，不可只做目录树评价。

### 默认排除

- `node_modules/`、`release/`、`tmp/`、运行时数据、缓存、日志、密钥和真实用户数据库。
- 与架构/命名无关的算法优化、视觉偏好、格式化、安全漏洞扫描和泛化代码质量清单。
- 仅因行数、函数长度、文件数量或个人偏好的目录布局提出整改。
- 已准确记录且仍符合迁移方向的 legacy 债务，不重复记为新发现；只评价其名称/边界是否仍会让新人误解，以及文档是否足以防止误用。

## 审查方法

1. **建立事实地图**：从文档路由到入口，再到 exports/imports、真实调用方、组合根、存储和页面引用。区分源码文件、兼容入口、运行时资源与生成物。
2. **核对目录内聚性**：目录名是否表示稳定领域或架构角色；文件是否放在实际 owner 下；shared 是否确实跨领域、稳定且无副作用；是否出现仅凭可达性跨域导入私有实现。
3. **核对文件职责**：文件名与默认/具名导出、主要工厂和真实消费者是否一致。`index.js`、`manager.js`、`service.js`、`runtime.js`、`controller.js`、`store.js`、`client.js`、`adapter.js`、`utils.js`、`helper.js` 等词必须按实际行为判断，不能见词就扣分。
4. **核对符号语义**：抽查每区关键符号及其调用点。重点查找：
   - 名称承诺的行为与实际行为相反或范围明显不同；
   - 名称混淆命令与查询、同步与异步、原始事件与领域事件、本地与远端、实时与快照、单个与集合、ID 与对象、时间与时长；
   - 布尔变量不能从名称判断 true/false 含义，或名称与判断方向相反；
   - 参数/返回值名与调用方使用的数据形态不符；
   - 同一概念在不同层使用多个近似名称且没有转换边界说明；
   - 同一名称承担不同概念，容易接错数据或调用错误 owner。
5. **区分公共契约与内部名称**：HTTP/WS/IPC 字段、持久化键、URL、外部协议字段即便不够理想，也不能直接建议重命名；应标明兼容成本，并优先考虑局部别名、注释或文档消歧。
6. **验证候选发现**：至少给出一个真实定义或调用证据；重要结论尽量给出“定义 + 使用/契约”双证据。不能仅凭文件名猜测函数行为，也不能把搜索命中当成架构违规。对错误字段沿调用链核对真实消费者，区分“API 回执错误”与“界面/日志已显示错误”；静态可确认的问题可用现有测试或模拟响应验证，不访问真实账号。
7. **运行适度检查**：可运行现有架构/文档门禁作为辅助证据。门禁通过只证明其覆盖范围，不代替语义审查；不得为本次只读审查创建新测试设施或运行真实账号/生产服务。

## 不过度审查的判定规则

- **确认问题**：名称或归属与当前事实冲突，已经或很可能造成错误理解；给出具体误读和证据。
- **轻微歧义**：代码可理解，但新人需要额外跳转才能避免误读；只给低成本消歧建议。
- **合理设计/已接受债务**：有明确 owner、兼容理由、保护测试或 ADR，不应要求立即整改。
- **观察而非问题**：可替代命名只是个人偏好，或改动收益小于公共契约/大量调用点的成本，不列入整改清单。
- **路径不是私有性证据**：Infrastructure 可以依赖纯领域契约。跨目录引用需核对导出职责、规范及状态/资源依赖，不因没有经过 `index.js` 或文件位于领域目录就认定越界，也不默认搬入 shared。
- **消费者数量不是归属判据**：只有一个消费者不自动意味着 shared 放错目录；需核对语义是否稳定、是否包含专属业务决策，以及 Accepted 规格记录的 owner。
- **同名不是数据冲突证据**：不同作用域的局部变量与配置字段同名，只有存在混用、错误转换或共同状态歧义时才计为跨层问题。
- **已有说明应影响结论**：兼容字段、历史目录、迁移注释和现行 owner 文档已能清楚解释的名称，优先作为记录项；可选直链、文件搬迁或更漂亮的名称不自动产生整改任务。
- **区分资源归属与资源故障**：显式调用工厂才创建资源，不等于导入即有副作用；目录规则偏离可以是边界债务，但不能据此断言泄漏、重复绑定或生命周期故障。
- 不建议大规模目录搬迁、统一改名、按行数拆分、引入框架/容器/服务，或为了“漂亮”破坏稳定 API、URL、IPC、存储键和 Electron 安全边界。

## 严重度

- **P1**：有证据表明存在严重行为、数据完整性或安全边界风险；不能仅以维护者可能误读作为依据。
- **P2**：已确认的行为/契约错误，或明确偏离现行架构规则且无合理例外的边界债务，值得针对性处理。区分功能错误和维护债务，不把普通内部命名偏宽、偏窄或同名自动提到 P2。
- **P3**：有具体依据的低风险命名/文档歧义，可随相关维护消歧；文档事实错误也可单独修正。没有实质收益时，不要求为完成清单独立改名。
- **记录项**：合理设计、已接受债务或无需行动的说明，不计入问题数。

证据可信度与严重度分开表达：确定存在一个旧名称，不代表它具有高影响。给出最小成本的处理方式；涉及依赖方向、状态 owner 或公共契约的建议，不能称为无需计划的机械改名，实施时遵循 `PLANS.md`。

## 报告结构

1. **结论摘要**：总体是否合适、新维护者最容易误解的点、是否建议结构性整改。
2. **基线、范围与方法**：当前工作树/提交、排除项、查看的区域、运行的检查及其局限。
3. **实际架构地图**：进程、组合根、领域、存储、Renderer、overlay、远端服务器和原生助手；解释目录与角色的对应。
4. **目录与文件审查**：分后端/存储、Electron、前端/页面列出准确之处和具体发现。
5. **变量、函数与跨层术语审查**：按“定义证据 → 使用证据 → 可能误读 → 建议”写清每个发现。
6. **合理设计与既有债务**：说明哪些看似可疑但有依据，避免后续重复审查。
7. **分级整改建议**：只列值得做的最小改动，区分可独立消歧与需随相关变更处理的项目；不制造大迁移。
8. **覆盖与限制**：明确没有检查什么、哪些判断仅由静态证据支持。

每个问题使用稳定条目格式：

```markdown
### [P2/P3] 简短标题
- 位置：`path/to/file.js:行号`（必要时再列调用方/文档）
- 证据：名称、实际行为与调用事实。
- 影响与边界：已确认的影响、已有消歧依据，以及尚未证明的运行时后果。
- 误读：新维护者可能作出的具体错误判断。
- 建议：最小、符合 owner 的消歧方式；公共契约需注明兼容约束。
```

报告末尾必须给出问题计数（按 P1/P2/P3）和一句明确结论：**保留当前架构并局部消歧**，或**需要结构性调整**；只有存在充分证据时才选择后者。
