# LIRA 当前工作树只读代码审计提示词

日期：2026-10-24。执行结果见[代码审计报告](2026-10-24-code-audit.md)。这是本次使用的审计任务说明，不改变仓库规范、已接受的架构或公开契约。

你是 LIRA 的只读代码审计员。请审计当前工作树中隐性的正确性问题、数据安全风险、代码结构缺陷、运行效率问题以及依赖与构建链风险。目标是用可复核的证据找出值得处理的问题，而不是凑发现数量、追求文件更短或引入新架构。审计完成后只提交报告，不直接修复。

## 1. 范围、事实来源与边界

- 审计 `D:\Work\Live` 当前工作树，包括未提交及非忽略未跟踪的源码；不能只审 HEAD、最近提交或已跟踪 diff。保留所有已有 staged、unstaged 和 untracked 内容，不回退、整理或覆盖。
- 遵循根目录及适用子目录的 `AGENTS.md`。意图优先级依次为当前明确需求、Accepted 规格、Accepted ADR、owner 架构/契约文档、测试与运行证据、现有实现。代码和测试通过只描述现状，不自动证明行为正确。
- 保持 Electron + Node.js 模块化单体、Electron 主界面和 OBS／哔哩哔哩直播姬浏览器源例外。区分 Bilibili 平台与直播软件；不要把已接受的架构决策、兼容边界或文件行数本身列为缺陷。
- 源审计排除 `node_modules/`、`tmp/`、`release/`、`dist/` 和生成素材，但应检查 `package.json`、`package-lock.json`、打包配置、构建脚本和原生依赖清单。相邻服务器仓库不自动纳入实现审计；已有固定契约检出可用于验证。
- 不修改业务实现、测试、配置、技术契约、用户指南或依赖锁文件；不提交、分支、发布或安装新工具。审计脚本、日志和中间证据只放仓库根目录 `tmp/` 下的专用目录。
- 不读取、迁移或复制真实用户数据库、Electron profile、Cookie、账号、密钥或生产数据；不访问生产服务，不执行破坏性操作、主动利用或超出本地合成证明的安全测试。秘密扫描结果只记录类型、位置和可信度，不复制秘密值。

## 2. 固定审计基线

1. 记录分支、HEAD、时间、Node/npm 版本和 Git 状态。为相关源码、测试、脚本、native/build、契约及清单建立内容寻址清单，覆盖非忽略未跟踪文件，由 `HEAD + 文件 SHA-256 清单` 派生快照 ID。
2. 工作树在审计期间可能变化。每项自动检查前后比较输入；变化时隔离旧结果，只重跑受影响检查。最终发现必须重新读取当前代码并核对行号，不得把不同快照的结果混为同一版本的证据。
3. 从 owner／事实地图、路由表、exports/imports/callers 和相关测试建立关键调用链。当前 diff 是优先线索，不是全部范围；历史报告和未结项台账只用于定位及去重，结论必须重新核实。
4. 建立 `候选 → owner/来源 → 快照 → 已知事项 → 所需证据 → 验证 → 处置` 台账。已知提案、延期验收和遗留债务只有出现新故障机制、扩大暴露或回归时才计为新发现。

## 3. 审计内容

### 正确性与数据安全

- 沿真实入口检查参数归一化、空值、错误分支、状态转换、分页/游标、排序及时钟语义。
- 核对 SQLite schema/migration、事务边界、跨库操作、部分提交、回滚、崩溃恢复、备份/清库和保留策略。
- 检查礼物、点歌、加班机、云同步等路径的幂等键、代次/fence、重复交付、异步接受顺序、提交后副作用及重启恢复。
- 对并发、取消、重试和 single-flight，必须检查迟到结果、超时、关闭/重开、账号切换和 dispose，而不只看正常路径。

### 认证授权与秘密

- 先检查 HTTP、WebSocket、IPC 和特殊 capability 路由的认证/授权顺序，包括绕过通用管线的预览、场景、媒体和静态资源入口。
- `streamerId` 是租户身份而非客户端授权证据，`roomId` 不是授权边界。检查 Bilibili 事件 ingress 是否绑定所属 runtime，管理、主播、设备、overlay 与公开访问是否保持最小权限。
- 核对 Host/Origin、session、redirect、frame/source、窗口打开、导航、权限请求和凭据注入；检查 renderer 是否可获得 Cookie、token、API key、任意文件或未受限特权操作。
- 保护 contextIsolation、safeStorage、session partitions、日志脱敏和 `local-media://` 精确来源检查。不可只因特殊路径先分发就认定未授权，必须验证其自身 guard 和 owner scope。

### 结构、生命周期与效率

- 检查组合根是否混入领域决策、跨域访问是否绕过 owner、公共模块是否携带无关副作用，以及同一规则是否存在已发生漂移的多个所有者。
- 检查窗口、进程、监听器、定时器、订阅、请求、缓存和子进程是否由创建者幂等清理。
- 查找有现实触发频率的重复全量扫描/序列化、同步 I/O、N+1 查询、无界队列/缓存及密集事件下的主线程或渲染开销。
- 文件长度、循环复杂度、同步 API 或重复代码只作为复审信号。性能缺陷必须有现实输入、调用频率和预算证据；只有复杂度推测时列为改进候选，不虚构提升百分比。

### 依赖与构建链

- 核对直接依赖实际用途、版本、许可证、运行时/开发归属、缺失声明、传递包直接引用及内部 API 耦合。
- 使用不带修复的依赖审计和现有锁文件；区分直接与传递依赖、客户端运行时与安装/开发/构建链。公告命中不等于 LIRA 可达漏洞，必须结合功能使用面、前置条件和打包范围分诊。
- 检查原生依赖清单和现有资产图，但不为了审计执行 restore、native build、安装器或发布。缺少传递依赖证据时明确记录覆盖限制，不把“存在新版”本身列为问题。

## 4. 自动检查与人工复核

1. 优先使用仓库已有的文档、语法、架构、契约、modularity advisory 和精确 focused tests；先区分缓存复用与新鲜执行。专用 SAST/secret 工具不可用时，不安装新工具，定向搜索只作为线索，不冒充完整扫描。
2. 自动检查只写允许的隔离缓存/证据目录。禁止 `npm audit --fix`、依赖更新和破坏性 Git 操作；不运行全量套件、发布/安装器、native build 或 roundtrip 来弥补证据不足。
3. 对候选至少读取实现、真实调用方、相关 guard、适用契约和相邻测试。子任务或搜索结果只是候选清单，主审计线程必须独立复核。
4. focused test 先精确列选并检查 helper 副作用，再使用合成数据及隔离 TEMP/TMP；测试前后核对输入快照。需要真实账号、生产服务或不成比例验证才能确定的结论保持未验证。
5. 只有具体性能候选属于现有合成基准的测量范围时才运行基准；结果不能外推为 Electron 主线程、真实设备或生产性能。

## 5. 证据门槛与分级

- **已确认（Confirmed）**：有当前可达路径、具体故障机制、guard 分析、被违反的契约或明确正确性、实际影响和精确位置。依赖公告可确认“受影响版本存在”，但不能据此声称对应攻击在 LIRA 已可利用。
- **条件性风险（Conditional）**：机制有代码依据，但触发前提、外部行为或影响尚未验证。明确缺失证据，不写成已发生故障。
- **改进（Improvement）**：可证实的维护、依赖或可测效率机会，但当前没有正确性/安全故障证据。说明收益、兼容成本和最小变更范围。
- **已排除/已知（Excluded/Known）**：已有防护、契约允许、不可达、误报、已接受决策或已有 owner/plan 的事项。保留排除理由，避免重复报告。

严重度使用 Critical / High / Medium / Low / Info，按数据安全和安全边界、运行时正确性、性能、结构维护性、依赖整理排序。只有能合理确定攻击向量、前置条件和影响时才使用 CVSS/CWE；不要给一般结构或性能建议伪造评分。

## 6. 报告与完成条件

每项发现包含：编号、标题、状态、严重度、精确文件与行号、触发路径、影响、实现/调用方/guard/契约证据、最小修复方向和建议验证方式。性能项另列测量条件与限制；依赖项另列直接性、依赖链、运行/构建归属和可达性。

最终报告包含：

1. 审计基线、执行摘要和按状态/严重度统计；
2. 证据化发现及分阶段处理顺序；
3. 效率、结构和依赖建议；
4. 非问题/已排除候选及已知事项去重；
5. 实际命令与结果、覆盖范围、未覆盖限制；
6. 报告和提示词链接，不声称建议已经实施或验证。

写入前确认报告文件名不冲突。最后复核所有位置、链接和计数，运行文档门禁、仓库级及报告范围的 `git diff --check`、完整 Git 状态和最终快照比较。确认本任务新增的受版本控制变更只有审计报告、提示词和报告索引，所有原有用户改动均保留。准确说明未运行的测试和不能证明的事项。
