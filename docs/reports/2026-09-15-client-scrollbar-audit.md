> 2026-09-17 规范调整：百宝箱收起后的图标侧栏（视口宽度 >900px）隐藏滚动条，保留滚轮、触控板和键盘滚动。展开导航及 ≤900px 的文字导航继续在溢出时显示滚动条；桌面强制颜色模式仍回退系统呈现。下文“恢复百宝箱导航提示”的要求以此例外为准。

## 一、结论

**建议 LIRA 采用统一的中性、圆角、低干扰桌面滚动条：主要操作区域有溢出时保留可见提示，鼠标靠近滑块或键盘聚焦当前滚动区时增强；展示画面隐藏操作性滚动条；由布局错误产生的滚动条通过修正布局消除。**

### 推荐方案定稿（待实施）

本节汇总本报告选定的设计方向，作为后续实施入口；不代表客户端已经完成这些改动。尺寸均为 CSS 像素，适用于桌面定制皮肤，系统回退的边界见第六、八节。

| 项目 / 状态 | 选定方案 |
| --- | --- |
| 统一规格 | 主工作区、列表、菜单、编辑框共用 **12px 滚动槽**；主要通过位置和职责区分层级，不再分别设置多档宽度 |
| 静止，有溢出 | 可见滑块 **6px**，暖灰 `#8C8279`，持续提供位置提示 |
| 悬浮 / 键盘聚焦 | 鼠标进入滑块的原生可操作范围，或键盘聚焦当前滚动区时，滑块增强为 **8px**、`#6F665E`；仅悬浮正文不触发整页增强 |
| 拖动 | 保持 **8px**，加深为 `#514942`；滚动槽始终不变宽，正文不随状态切换移动 |
| 外形 | 简单胶囊形、透明轨道、无上下箭头；无溢出时不显示滑块或轨道装饰 |
| 队列布局 | 按窗口与播放器占用后的可用高度分配较紧凑的空间；相同布局条件下，空、少量、长队列保持同一高度，两栏对齐，长内容内部滚动 |
| 展示与系统边界 | OBS / 自动歌词展示按用途隐藏操作性滑块；强制颜色模式回退系统呈现；固定尺寸皮肤不承诺完整沿用系统自动隐藏行为 |

**空队列排版：**保留稳定的队列区域，在其中简洁表达等待状态。原建议的总高 140–180px 仅保留为需重新设计排版的候选，不作为默认尺寸；若采用，必须同时缩小插画、简化文字与间距，不能只压缩外层高度。最终高度按首批记录的可读性和下方歌库入口的可达性验证，详见 5.2。

**实施顺序：**先恢复必要提示、修复已确认的横向溢出及重复纵向阅读路径；再用点歌主区和一个长列表确认统一皮肤，并扩展到其他操作区域；队列高度与空态作为独立布局批次验证，随后梳理展示例外。

优先处理以下事项：

1. **恢复必要提示。** 百宝箱导航、主播工作台正文、任务和备忘列表目前存在永久隐藏滚动条的规则。内容超出后，用户容易误以为已经看到全部。
2. **消除无意义的横向滚动。** 开播动画、萌时钟等表单在最小桌面尺寸下仍保留宽双栏，应该按实际内容空间换行。
3. **缩短点歌页的无效滚动距离。** 空队列仍占用整块固定高度，歌库入口因此被推到较低的位置。应缩减无效空白，并采用按可用空间分配、消息增删不改变外部高度的队列策略。
4. **统一最终生效的样式。** 当前同时使用系统默认、标准 CSS 滚动条属性和 WebKit 伪元素，部分局部样式会被桌面主题的继承值覆盖。
5. **明确编辑与展示的区别。** 设置表单、历史记录、选择菜单需要操作提示；自动跟随歌词、OBS 展示内容通常不需要显示鼠标操作用的滚动条。

## 三、参考 Apple 与 Microsoft，应该学什么

### 3.1 Apple：视觉克制，同时让内容可发现

Apple 的 Scroll views 指南强调：让人知道还有内容可滚动，支持熟悉的手势与键盘操作，并尽量避免同方向滚动区域相互嵌套。滚动指示器可以短暂出现，内容边缘也可以提供延续提示。[Apple HIG：Scroll views](https://developer.apple.com/design/human-interface-guidelines/scroll-views)

**适用于 LIRA：**淡化轨道、使用简单圆角滑块、减少卡片套卡片的纵向滚动、让下一部分内容露出合理的边缘。

macOS 提供根据鼠标/触控板自动显示、滚动时显示、始终显示等选项。因此“Apple 风格”不能简化成把全部滚动条永久隐藏。[Apple：Appearance settings](https://support.apple.com/guide/mac-help/change-appearance-settings-mchlp1225/mac)

### 3.2 Microsoft：适合鼠标的明确操作反馈

Microsoft 的 Scroll viewer 根据输入方式区分细的滚动指示器和可直接拖动的滑块；鼠标靠近指示器时可展开为可操作形态。指南也提醒不要让覆盖式滚动条挡住内容。[Microsoft：Scroll viewer controls](https://learn.microsoft.com/en-us/windows/apps/develop/ui/controls/scroll-controls)

**适用于 LIRA：**主界面按鼠标操作优化；重要列表即使在静止时也保留可发现的提示；交互时增强滑块；给最右侧按钮、数字和表格列留出空间。

### 3.3 推荐方向

采用 **Apple 的简洁外观，加上 Windows 桌面工作软件的可发现性与拖动便利性**。LIRA 是直播时频繁操作的工具，滚动条应帮助用户迅速判断记录数量、当前位置和剩余内容。

不建议用彩色发光、渐变、纹理、拟物金属、装饰图标来美化滚动条。队列的金色/青绿色、按钮的红色已经承担业务区分，滚动条不需要再表达一套分类。

## 四、全客户端逐区域取舍

### 样式代号

| 代号 | 用途 | 显示策略 |
| --- | --- | --- |
| A 主滚动 | 工作区、长设置正文 | 有溢出时保留中性可见滑块，交互时增强 |
| B 局部滚动 | 队列、菜单、目录、长文本框 | 内容超过上限后显示与 A 同规格的中性滑块，保留拖动能力 |
| C 沉浸展示 | 自动跟随歌词、OBS 展示 | 默认不显示操作性滚动条；内容仍需完整、合理地展示 |
| D 数据横滚 | 多列表格、原始数据 | 只有列宽确有需要时出现，明确提示左右还有内容 |

“保留”均指**保留必要时出现的能力**，不要求空列表或完全装得下的内容也显示滑块。

A/B 区分滚动职责，不分别建立宽度、颜色皮肤；D 的横向滚动复用同一槽厚与交互状态，C 按展示用途处理。

## 五、已确认的重点问题

### 5.1 [P2] 长内容存在，但滚动提示永久隐藏

**位置：**百宝箱导航、工作台正文、任务和备忘列表。

在 1280×720、播放器收起、导航展开的布局样本中，导航可视高度约 645px，内容还超出约 313px；最小尺寸下可视高度约 605px，超出约 353px。其计算样式始终为 `scrollbar-width:none`。

加入 30 条合成任务/备忘后，工作台正文、任务列表、备忘列表均出现真实纵向溢出，仍没有滑块。

**建议：**导航和长列表恢复中性细滑块；主工作台恢复主滚动提示。可以降低视觉权重，但不能把功能可发现性完全交给用户猜测。

### 5.2 [P2] 空队列放大了主页面的滚动负担

**位置：**点歌 `.queues-row`。

桌面默认 `flex-basis` 和高度都是 450px；在高度 ≤700px 时仍有 418px。与下方管理区至少 420px 的高度叠加后，小窗口里自然需要大量向下滚动。

在无业务数据、播放器收起的布局样本中，点歌主区域的可视高度/内容高度分别为：

| CSS 视口 | 主区域可视高度 | 内容高度 | 需要额外滚动的距离 |
| --- | ---: | ---: | ---: |
| 1280×720 | 662px | 1209px | 547px |
| 1024×680 | 622px | 1331px | 709px |
| 1920×1080 | 1022px | 1209px | 187px |

这些是结构样本测量，不代表每个真实账户的页面长度。

**推荐策略：**按窗口高度及播放器占用后的可用空间，为队列分配较紧凑、稳定的区域。窗口、播放器状态等布局条件相同时，空、少量、长队列共用同一高度；内容超出后只在列表内部滚动。两个并列面板保持对齐，首条消息到达、消息持续增加或队列清空时，不能因队列高度切换把下方歌库、设置及正在点击的按钮推走。保留用户主动触发的既有布局操作。

原建议的 **140–180px 总高偏紧，不作为默认方案**。当前队列标题最小高度为 72px，空态插画为 68px，尚未计入文字、间距和正文内边距。若继续评估这个紧凑候选，必须同时缩小插画、简化空态排版，并验证按钮换行及内容到达后的稳定性，不能仅改外层 `height`。[song.css:388](D:/Work/Live/public/css/admin/workspace/song.css:388)、[song.css:733](D:/Work/Live/public/css/admin/workspace/song.css:733)

最终队列高度尚待布局验证，以首批记录可读、歌库入口不被大块空白推远为依据；在报告列出的三个窗口尺寸及播放器状态下分别检查。新消息到达不触发空态与有数据状态之间的外部高度切换。

在工作区可视高度不变时，减少无效空白会缩短页面的可滚动距离；若仍有溢出，滑块通常会变长；内容全部装得下时不再显示滑块。不能在下方仍有内容时直接去掉主滚动提示。

### 5.3 [P2] 最小桌面尺寸下出现不必要的横向滚动

**开播动画：已确认布局原因。** 1024px 宽度下，右侧面板可用宽度约 709px；内部布局仍要求 `350px + 430px + 16px`，再加正文内边距后内容宽度约 832px，横向超出约 123px。画面右侧控件和预览需要左右拖动才能看全。

其单列断点在 920px，低于客户端默认最小窗口宽度。断点按整窗判断，未充分考虑左侧导航占用的宽度。[start-animation.css:559](D:/Work/Live/public/css/admin/other-features/start-animation.css:559)

**萌时钟：已确认同类风险。** 双栏最小列宽为 360px 和 320px，间隔 24px；最小窗口样本出现约 15px 横向溢出。单列断点为 980px，同样低于默认最小窗口宽度。[clock.css:11](D:/Work/Live/public/css/admin/other-features/clock.css:11)、[clock.css:396](D:/Work/Live/public/css/admin/other-features/clock.css:396)

礼物姬右侧正文在同一布局样本中还出现约 18px 横向溢出，需要在完整初始化的控件状态下进一步定位；本报告将它列为复核项。

**建议：**按右侧容器可用宽度决定单/双列，或采用不会撑破容器的列宽下限；先修布局，再限制不需要的横向溢出。直接隐藏横条会留下被裁掉的控件。

### 5.4 [P2] 源码里的“6px 粉色”不等于实际看到的样式

队列基础 CSS 写有 6px 的 WebKit 滚动条与粉色滑块；桌面主工作区又设置了 `scrollbar-color:rgba(117,102,91,.34) transparent`，该值会向后代继承。[collapsible.css:106](D:/Work/Live/public/css/admin/collapsible.css:106)、[desktop.css:447](D:/Work/Live/public/css/overlays/desktop.css:447)

在 Electron 43 的 20 条队列样本中：

- 当前规则下，实际滚动槽占用 **15 CSS px**。
- 仅在隔离样本上临时把该列表的 `scrollbar-color` 改回 `auto`，滚动槽变成 **6 CSS px**。
- 空队列没有溢出，滚动槽占用为 **0**。

这与标准属性覆盖 WebKit 样式的行为一致；`scrollbar-color` 的继承尤其容易被遗漏。[MDN：WebKit scrollbar 与标准属性的关系](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Selectors/::-webkit-scrollbar)

**建议：**统一样式时集中处理继承和覆盖顺序，不再逐个文件补颜色、宽度。桌面歌词表单同时写 `thin` 与 WebKit 12px，也不应被理解成最终必然是 12px。

### 5.5 [P2] 桌面歌词设置存在重复的纵向阅读路径

1280×720 的样本里，外层点歌区需要滚动约 505px，内层歌词设置表单又超出约 1354px；用户需要先滚到设置位置，再在较短的表单窗口里继续滚。

**建议：**现有页面结构下优先让表单融入主工作区，预览在合适宽度下保持可见。若未来把歌词设置独立成固定工作台，再让表单拥有唯一主滚动区；不要在本次样式统一时顺手增加一套页面架构。

## 六、推荐的统一视觉规范

以下为 **LIRA 选定的桌面皮肤建议值**，不是 Apple 或 Microsoft 对所有应用规定的像素尺寸，尚需在目标 Electron 中完成验收。A/B 共用一套规格，主要通过位置和职责区分层级；D 横向滚动复用同一槽厚及颜色。

| 项目 | A/B 主区、列表、菜单、编辑框 | C 展示 |
| --- | --- | --- |
| 滚动槽宽度 | 统一 12 CSS px；实际拖动命中范围单独验证，不把槽宽直接等同于可抓取宽度 | 默认无操作性轨道 |
| 可见滑块宽度 | 静止 6px，悬浮 / 键盘聚焦 / 拖动 8px；在固定槽内改变视觉宽度 | 手动浏览状态可短暂使用 B |
| 形状 | 简单胶囊形，圆角一致 | 同左 |
| 颜色 | 共用中性暖灰，与当前奶油色桌面协调；不按业务或区域另设色系 | 随深浅背景调整 |
| 轨道 | 透明，不用强边框或装饰 | 隐藏 |
| 滑块长度 | 反映可见内容比例；保留可抓取的最小长度，短菜单不能只剩一个点 | 不适用 |
| 悬浮 / 焦点 | 仅增强鼠标靠近滑块或正在接受键盘操作的滚动区；不因正文悬浮触发整页增强 | 有明确手动交互时才出现 |
| 拖动 | 保持 8px，颜色加深，保留原生拖动反馈 | 按交互模式决定 |
| 上下箭头 | 定制皮肤不显示；系统回退保留系统形态 | 无 |
| 动效 | 如需过渡，约 120–160ms，仅改变颜色/透明度；槽宽、正文布局不参与动画 | 不为显隐增加装饰动画 |

### 颜色建议

浅色工作界面选定以下状态组合：

- 静止滑块：`#8C8279`
- 悬浮/焦点：`#6F665E`
- 拖动：`#514942`
- 轨道：透明

在当前浅色表面 `#FFFCF8` 上，前两者对比度分别约为 **3.68:1、5.49:1**。当前主工作区使用的 34% 透明暖灰，在同一纯色背景上的估算对比度约 **1.60:1**，可以解释滑块较淡的观感；实际背景有变化，应按最终合成颜色复核。

深色歌词/播放区域使用同一语义的较亮中性色，不把浅色数值原样复制过去。避免根据 SC、点歌、AI 等业务分类给滚动条分别上金色、青色、粉色。

对于作者自定义的必要控件视觉，需要关注非文本对比度；原生未修改控件及具体例外应按标准判断，不能仅凭一张截图给整个应用作合规结论。[W3C：Non-text Contrast](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html)

### 显示规则

1. **无溢出：**不显示滑块。稳定布局所保留的槽位不等于一根应该显示的滚动条。
2. **有溢出的主区与重要列表：**默认保留 6px、可辨识的滑块。鼠标进入滑块的原生可操作范围或键盘聚焦当前滚动区时增强为 8px；拖动时加深。仅悬浮正文、滚动其他区域，不让整页多根滑块同时增粗；嵌套区域的焦点样式也应限定到当前操作区。
3. **菜单、抽屉和对话框：**内容超出后立即提供提示，不能要求先尝试滚动才能发现剩余选项。
4. **纯展示内容：**隐藏滑块，使用已有的自动跟随、轮播、裁切或自适应机制表达内容。
5. **系统与辅助功能：**使用原生滚动机制，强制颜色模式回退系统呈现；键盘仍能到达并操作必要滚动区域。固定尺寸皮肤与系统自动隐藏的取舍见下文，不作未经验证的偏好兼容承诺。

细滑块的视觉宽度和可操作区域不是同一个参数。不要仅凭“看起来只有 6px”宣称它已经足够容易拖动，也不要误把所有原生滚动条都机械地改为 24/44px。WCAG 的目标尺寸规则存在用户代理控件等例外；自制滚动控件需要单独评估。[W3C：Target Size (Minimum)](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)

### 系统显示偏好的边界

指定 `::-webkit-scrollbar` 的宽度或高度会把覆盖式滚动条转为占用槽位的传统呈现。因此，本报告选择的固定 12px 皮肤不能同时承诺完整沿用系统自动隐藏行为；透明轨道也不等于覆盖式滚动条。[Chrome：Scrollbar styling](https://developer.chrome.com/docs/css-ui/scrollbar-styling)

常规桌面操作区以固定槽宽和有溢出时可发现为目标；强制颜色模式解除定制，回退系统配色与形态。其他系统显示偏好是否被保留，需要在实际目标系统及 Electron 版本上验证并记录。需要完整沿用系统呈现的范围应选择原生默认样式，并接受其宽度、箭头及显隐由系统和引擎决定；本次不据此新增用户设置或平台适配层。

## 七、CSS 改动容易再次引入的问题

| 风险 | LIRA 中的具体关联 | 后续修改要求 |
| --- | --- | --- |
| 只设置 `overflow-y:auto`，横轴也变成可滚动 | 队列、百宝箱正文、开播/时钟等容器的计算横轴可为 `auto` | 两个方向一起检查；先处理列宽、换行和长内容，再限制不需要的横轴 |
| 给普通卡片添加 `max-height` 和 `overflow:auto` | 点歌主区、歌词设置、工作台列表已经存在父滚动区 | 每个新增滚动容器说明它为什么需要独立操作；优先释放普通正文 |
| 改动固定高度计算 | 多处使用 `100vh - 58px - --player-dock-height` | 顶栏变高、播放器展开或字体变化时复核剩余高度，避免根滚动、内容遮挡或空白尾部 |
| 按整窗断点判断侧栏右边的双栏布局 | 开播动画、萌时钟 | 以容器宽度或真实可用宽度决策；导航展开和折叠都要成立 |
| Grid/Flex 子项保留内容最小宽度 | 长用户名、模型名、网址、歌曲备注，固定下限的网格 | 按实际需要使用 `min-width:0`、`min-height:0`、`minmax(0,1fr)`、正常换行；避免无差别裁剪 |
| 标准滚动条属性和 WebKit 样式互相覆盖 | 队列、搜索、歌词设置、分析菜单 | 同一元素选择明确的生效路线；把继承值纳入检查 |
| 全局隐藏所有滚动条 | 会波及菜单、编辑框、目录、分析表和诊断数据 | 显示策略按区域职责定义，不能用通配规则统一隐藏 |
| 把根 `body` 改为 `overflow:auto` | 正常桌面本来由工作区滚动；≤900px 又切换为根滚动 | 不把它当通用修复手段。页面缩放触发断点时确认只保留预期主层 |
| 普通弹层开到容器边缘 | 菜单采用局部绝对定位，部分卡片通过打开状态释放裁剪 | 保持已有的选择器及定位约定；不能为消除滚动条把菜单一并裁掉 |
| 轨道出现或交互状态变化时挤窄正文 | 表格、列表、表单和窄菜单 | 需要稳定对齐的位置可用 `scrollbar-gutter:stable`；悬浮、聚焦和拖动始终保持 12px 槽宽；不要对所有卡片都强制双侧留白 |
| 祖先容器的悬浮 / 焦点触发全部滑块增强 | 主工作区内嵌套队列、菜单、编辑框 | 仅增强当前操作区，避免用整页 `:hover` 或未经限定的祖先焦点规则批量增粗 |
| 新消息触发队列外部高度变化 | 队列下方紧接歌库、设置及操作按钮 | 同一布局条件下保持空、少量和长队列高度一致；消息增删不推移下方操作区 |
| 浮层滚到底后后方页面也移动 | 抽屉、选择列表、长明细 | 按实际边界设置滚动链策略；普通主页面队列则保留现有边缘释放行为 |
| 修改共享歌词/Overlay 规则 | 管理预览、独立歌词窗、OBS 可能复用同一类名 | 按编辑/展示模式限定样式，保持自动跟随和窗口用途 |

两个容易混淆的技术事实：

- `scrollbar-width:none` 隐藏滑块，但元素仍可以滚动；`overflow:hidden` 和 `overflow:clip` 的程序化滚动能力也不同。不要把它们当作等价的隐藏写法。[MDN：scrollbar-width](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/scrollbar-width)、[MDN：overflow-y](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/overflow-y)
- `scrollbar-gutter:stable` 为传统滚动条保留空间，对覆盖式滚动条不产生同样效果；它不能保证所有系统显示完全相同的槽位。[MDN：scrollbar-gutter](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/scrollbar-gutter)

长内容、Flex 最小宽度和浮层滚动边界的检查，也参考了 [Vercel Web Interface Guidelines](https://raw.githubusercontent.com/vercel-labs/web-interface-guidelines/main/command.md)。其中面向通用网页的建议按 LIRA 桌面场景取舍，不额外引入移动端重做或新依赖。

### 第一批：修正必要提示和已复现的布局问题

### 第二批：统一基础样式

在 [styles-base.css](D:/Work/Live/public/css/styles-base.css) 建立少量滚动条语义变量，在桌面主题 [desktop.css](D:/Work/Live/public/css/overlays/desktop.css) 指定中性色。主区与局部列表复用统一的 12px 槽宽、6px / 8px 滑块及状态颜色；展示区域按用途限定规则。

先以点歌主工作区和一个有溢出的长列表验证静止、悬浮 / 键盘聚焦、拖动三种状态及正文位置稳定性，再扩展到其他操作区域；这一步不混入队列高度调整。

实现路线建议为：**原生滚动机制 + 集中管理的 CSS 皮肤**。不增加模拟滚动、拖拽同步或整套滚动条依赖。

- 常规桌面操作区采用集中管理的 WebKit 皮肤，实现固定槽宽、胶囊形滑块和无箭头目标；在对应元素上处理标准属性的 `auto` 回退及继承，避免两条路线互相覆盖。
- 标准 `scrollbar-width` / `scrollbar-color` 或原生默认样式用于相应兼容、系统回退范围；接受宽度与箭头形态由引擎、系统决定，不宣称回退后仍满足定制像素值。
- 交互时只在固定 12px 槽内改变滑块视觉宽度和颜色，避免正文左右跳动；触发范围限定在当前操作区，不用整页悬浮规则统一增粗。
- 按第六节验证强制颜色回退及其他系统显示偏好的实际表现；不能把“原生滚动机制”写成“完整沿用系统自动隐藏行为”。

### 第三批：独立验证队列布局，梳理展示例外

- 队列布局单独实施、单独验证：按可用高度分配更紧凑的稳定空间，空、少量和长队列共用同一高度，保持并排对齐；验证首条消息、持续新增及清空均不因高度切换推移下方操作区。
- 队列最终高度依据实际排版确定；若评估 140–180px 紧凑候选，同时调整插画与空态文字间距，不直接套用到现有标题和插画上。
- 普通价格预览、短确认明细和普通通知减少内部滚动。
- 将 OBS 与独立歌词窗的显示策略按用途明确限定。

其中队列高度、歌词设置层级及 OBS 默认呈现属于可见行为调整，实施时应同步更新受影响的布局断言；现有测试通过并不表示设计建议已经实现。
