# LIRA 客户端第二轮优化审查提示词

日期：2026-10-03。用途：在了解当前客户端结构后，对冗余、遗漏复用和不必要的运行开销进行第二轮审查。以下提示词可直接复制使用；它不是已批准的重构计划。

## 可复制提示词

你正在审查 LIRA 客户端。请以“保持正常运行与现有契约”为前提，找出值得处理的冗余代码、未复用的相同职责，以及有证据的不必要计算、请求、渲染或资源占用。本轮先审查并输出报告，不修改业务代码。

### 1. 范围与基线

- 遵守根目录及命中目录的 `AGENTS.md`。以当前工作区为基线，包含相关未提交和未跟踪源码；记录 HEAD、日期及已有改动，不能用历史报告代替现状。
- 范围是当前客户端仓库：`public/js/`、关联的 `public/pages/` / `public/css/`、`src/electron/`、内嵌本地后端及其 `src/shared/`、领域和存储调用链。`scripts/`、`test/`、构建配置用于核对入口、消费者和验证方式。
- LIRA Server 是外部契约依赖；不修改、不顺带审查服务器仓库，也不建议直接跨仓 import。排除依赖包、构建产物、日志、用户数据库、凭据和其他真实运行数据。
- 从 `docs/reference/README.md` 的事实地图和 `docs/architecture/engineering/ai-workflow.md` 定位 owner，再追踪定义、调用方和相关测试。规格、Accepted ADR 与当前明确要求优先于现有实现。

### 2. 先核对已有机制

先确认当前已有能力，避免重新实现：

- Admin 的 `StateService`、`createAdminStateRenderer`、`EventBus`、组件草稿同步、`createToolboxLifecycle` 与兼容桥。
- `public/js/shared/` 中的提示、请求、表单、主题、礼物展示、歌词时钟和帧调度能力；overlay 已有主题和滚动工具。
- `src/shared/` 的纯规则、身份 facade、存储事务 owner、Electron 资源创建者的清理职责，以及同步控制器的取消/过期结果保护。

### 3. 按三个方向筛选

**A. 冗余与失效路径**

- 检查未使用的局部函数、导入、状态、旧适配层、无职责的转发和不可达分支。
- 删除建议必须追踪具名/命名空间导入、聚合导出、对象属性、动态 import、字符串注册、HTML/script 入口、桥接/IPC 和打包入口。
- “只出现在一个文件”不等于没有内部调用；“没有普通 import”不等于没有副作用加载；只有测试消费者也需要说明是否是契约测试入口。
- 分开判断“实现可以删除”“仅 export 可收窄”和“有意兼容应保留”。不能为了删代码取消功能、安全检查或恢复路径。

**B. 相同职责未复用**

- 找到两个以上真实调用链中重复维护的同一规则，优先检查已有 owner/helper 是否可以直接复用。
- 逐项比较输入、默认值、空值、数值转换、单位、返回形状、错误、同步/异步语义、副作用与资源所有权。
- 优先复用同领域现有实现；新增小型共享函数必须有明确消费者和稳定语义，不能建立通用框架、依赖袋或新的万能 `utils`。
- 不合并只是外观相似的逻辑。跨信任边界校验、独立登录分区、不同同步控制器、数据库迁移历史、CJS/浏览器 ESM 边界及现有跨运行时一致性保护，都可能是合理重复。

**C. 有证据的运行开销**

- 追踪重复请求/查询、循环内重复查找或分配、无变化时的序列化/DOM 更新、重复监听/定时器，以及离开界面后仍持续工作的资源。
- 写出触发条件、调用频率或规模、现有去重/缓存/可见性保护、可减少的具体工作。不要仅因看到 `JSON.stringify`、`setInterval`、嵌套循环就判为问题。
- 性能收益优先使用确定的调用次数、DOM 写入次数或复杂度证据。没有测量，不能声称卡顿、泄漏、显著提速或给出百分比。
- 缓存和跳过更新建议必须说明失效条件，包含账号/房间切换、重连、设置改变、歌词跳转、数据修正和失败重试等适用情况。

### 4. 每项建议必须包含

1. **位置与 owner**：文件、符号、审查时行号及相关消费者。
2. **证据级别**：静态已确认、隔离复现，或待验证；可疑项不能混入确定结论。
3. **触发与成本**：怎样走到该代码，重复维护或不必要工作具体在哪里。
4. **最小建议**：删除/直接复用/局部提取/减少重复工作；若已有实现不能复用，解释具体差异。
5. **收益类型**：可读性、减少维护点、减少请求/分配/渲染等；不要将行数减少等同于性能提升。
6. **行为不变量与风险**：哪些输入输出、错误、时序、边界或资源清理必须保持；是否涉及高风险契约。
7. **验证方法**：相关现有测试、必要的最小隔离复现，以及实施后应补的缺口。
8. **处理建议**：优先处理、普通候选、低收益暂缓；只有实际缺陷使用 P0–P3 严重性标签。

同一根因合并为一项。没有值得处理的问题时直接说明，不凑数量。

### 5. “不影响正常运行”的具体约束

- 保持公开 HTTP/WS/IPC 的路径、字段、事件、错误和权限，页面 URL、设置键、持久化格式、排序、输入接受范围、失败可见性与现有用户行为。
- 保持 Electron 的 context isolation、safeStorage、会话分区、受限桥、`local-media://` 来源校验及关闭时的保存顺序。
- 保持身份/来源隔离、事务原子性、礼物结算幂等、游标连续性、重连恢复及过期异步结果拒绝；不把正确性保护当成开销直接删掉。
- 保持表单草稿、焦点/选择状态、可访问性、动画节奏与 reduced-motion 行为。不以降低刷新频率、删动画或忽略事件冒充等价优化。
- Electron 是普通界面的验收运行时；OBS / 哔哩哔哩直播姬的 overlay 按浏览器源契约验证。不为审查重启用户应用、操作真实账号或读写真实用户数据。

### 6. 执行与输出

1. 建立源码与模块清单，说明排除项；扫描只是候选发现，不代表逐文件人工审完。
2. 按“冗余、同职责复用、运行开销”完成调用链复核，并主动寻找反例。历史建议必须重新确认仍存在。
3. 对关键结论运行已有的定向离线测试，或在 `tmp/` 中用真实模块和合成输入做最小复现。先检查测试副作用，不安装依赖、不写自动修复、不默认启动 Electron/浏览器或跑全套。
4. 输出审查报告：基线/范围、按收益与风险排序的确定发现、待测线索、合理重复与撤回项、实际验证结果及未覆盖区域。每项提供可定位的证据。
5. 检查本次文档 diff、`git diff --check` 和工作区状态；保留已有用户改动。最终简要列出最值得做的几项和报告路径。

如果之后明确要求实施，再逐项修改 owning module，并按风险验证；涉及契约、持久化、认证、生命周期或复杂并发的修改先遵循 `PLANS.md`。不能把“测试通过”写成“保证零风险”。
