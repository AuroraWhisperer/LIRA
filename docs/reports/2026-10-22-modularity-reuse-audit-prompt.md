# LIRA 模块化与公共能力复用审计提示词

日期：2026-10-22。执行结果见[审计报告](2026-10-22-modularity-reuse-audit.md)。这是本次使用的审计任务说明，不改变仓库规范或已接受的架构。

你是 LIRA 仓库的架构审计者。目标是找出真正值得提取、合并或调整归属的能力，让后续维护和调用更直接；不要把文件变短、目录变多、消除所有相似代码当作目标。

## 范围与约束

- 审计当前工作树的 `src/`、`public/js/`，必要时追踪 CSS、脚本、测试及唯一归属文档。当前仓库为 `D:\Work\Live`；不把相邻服务器仓库自动纳入范围。
- 先读根及相关目录的 AGENTS、事实地图、owner/contract/consumer/test 路由表、模块化规范和已登记遗留边界。
- 保持模块化单体、Electron 主界面及浏览器源例外，区分 Bilibili 平台与 OBS/直播姬应用。
- 本轮只审计；不修改业务实现、不提交、不分支、不改变 HTTP/WS/IPC、存储或安全契约。保留所有已有工作树改动。

## 执行方法

1. 建立生产入口、领域 owner、适配器、存储和共享模块的调用地图；优先利用已有架构检查，不以检查通过替代语义审查。
2. 按目的、符号和调用方查找已有实现，再检查：同一规则多处维护、已有公共能力未被使用、组合根混入业务策略、领域反向依赖、共享模块携带领域职责、一个模块拥有多个独立变化原因。
3. 每条候选至少检查实现、真实消费者和相邻测试；若建议公用，证明存在至少两个语义一致的消费者。单一消费者只有在保护明确边界时才值得抽取。
4. 区分相同语义与表面相似。权限、租户身份、事务、取消/重试、计时器和清理的所有权不能因复用而混淆。不同环境或不同协议的代码不要强行共用。
5. 用具体变更场景解释成本：调整哪条规则会要求同时改哪些位置、有什么漂移或调用风险。优先扩展已有 owner；不用通用 utils、依赖袋、万能控制器或新服务掩盖归属问题。
6. 对每条结论提供文件和符号、行号、证据、最小调整方向、收益、兼容与生命周期风险、验证方式；标记“已确认”“建议候选”或“暂不调整”。历史报告只能用于定位，须重新核对当前代码。
7. 执行与结论直接相关的现有检查。结构检查不能证明 UI 实测、账户行为、生产服务或性能；不启动用户应用，不接触真实用户数据，不为了审计运行全量套件。

## 输出与完成条件

- 提供范围、基线和限制；保留这份提示词。
- 优先级使用 P1（明确行为/数据/安全风险）、P2（可证实的维护成本或契约漂移）、P3（可选整理）。没有证据时不制造 P1。
- 只列有证据的结论，不凑数量；另列已排除的过度抽象，解释保留理由。
- 建议按独立的小批次排序，给出 owner、受影响消费者/测试/文档及完成标准。建议不等于已接受设计或已完成整改。
- 最终检查 diff、`git diff --check` 和工作树；确认原有改动保留、只新增审计产物，准确报告实际运行的验证。
