# LIRA 客户端礼物界面：布局与使用频率评审报告

日期：2026-09-14

状态：设计建议，尚未实施

对象：电脑操作不熟练、主要在直播过程中使用 LIRA 的主播

评审范围：当前工作区的礼物主页面、相关布局与交互，以及 Apple 官方设计资料。配套交互示意见本任务回复。

## 结论

**建议把礼物页组织成“日常直播概览＋按需打开的详情与设置”。最近礼物占主要空间，接收与统计状态保持可见，盲盒只展示必要摘要；冲刺在用户需要时展示进度，盲盒映射进入高级设置。**

当前问题成立，但“所有词条都向下展开”还不是最准确的描述。当前页面主要按功能清单纵向排列：既有需要反复看的实时信息，也有只需偶尔修改的表单；它们占据相近的视觉层级。于是，横向空间没被有效利用，纵向又显得很长。没有数据时，较大的空状态进一步放大了空白感。

你补充的两点决定了改版的重点：**盲盒映射通常不看，月底冲刺只在特定阶段才需要。** 因此，解决办法应当先改变各功能的默认呈现方式，再调整排列、间距和装饰。只把卡片做小、改成两列或增加折叠按钮，都只能解决一部分问题。

建议保留一定留白，让直播中的扫视更轻松。需要去掉的是没有信息价值的占位、无关表单和反复寻找入口的成本，不以“把每个角落填满”为目标。

现有界面也有值得保留的基础：礼物图像与观众信息有业务辨识度；“最近礼物→全部流水”“盲盒摘要→完整分析”已经存在；复制链接有反馈，重置进度有确认。改版可以沿用这些能力。

## 按频率、时机与后果分配位置

仅用“高频／低频”还不够。一个操作可能很少点击，却需要始终看见状态；一次少见的连接异常，也可能比高频的普通数据更需要注意。

因此，每项功能应分别回答：**多久看一次、多久改一次、什么时候需要、出问题的后果是什么。** 除你明确提供的映射与冲刺习惯外，下表的频率都是针对直播场景的初步假设，后续可根据实际使用调整。

| 功能 | 查看频率／操作频率 | 需要的时机 | 推荐位置与默认状态 |
|---|---|---|---|
| 礼物检测与相关连接状态 | 可能经常确认／很少切换 | 开播前、直播中、异常时 | 顶部紧凑状态区；异常能在原位置看见 |
| 礼物提示开关 | 偶尔确认／偶尔调整 | 不想被提示打扰时 | 顶部保留小型开关，并说明关闭提示不会等于清空数据 |
| 最近礼物 | 高频查看／很少编辑 | 收礼与答谢时 | 主区域，默认展开，优先显示观众、礼物、数量与时间 |
| 全部礼物流水 | 按需查找／按需筛选 | 追溯、核对时 | 最近礼物标题旁的固定入口，复用现有抽屉 |
| 今日盲盒摘要 | 有盲盒互动时较高／很少修改 | 观众询问盈亏时 | 次要区域保留简短摘要；明细进入分析工作区 |
| 盲盒观众排行与开盒明细 | 因直播内容而异 | 专门查看盲盒时 | 既有盲盒分析入口；若盲盒是主要内容，允许主动切到该工作区 |
| 月底冲刺 | **用户确认：阶段性需要** | 用户开展冲刺活动时 | 未使用时小入口；主动显示后保留进度，调整表单按需打开 |
| 观众画面／投屏配置 | 预览与复制按需；编辑集中发生 | 首次设置、换版式、重新添加来源时 | 清楚的“投屏设置”入口；打开后直接看见预览与复制 |
| 盲盒映射 | **用户确认：通常不看** | 特殊规则维护时 | “更多设置→盲盒配置”，默认说明官方规则自动同步 |
| 手动 ID、产物编码、JSON | 极低频专业操作 | 确实需要自定义时 | 明确的高级编辑入口之后 |
| 收包、命令名等诊断 | 普通直播中低频 | 排查问题时 | 诊断详情；普通状态区只给可理解的状态与处理入口 |

有两个容易混淆的例子：

**检测开关可以小，检测状态不能难找。** 不能因为用户很少点击开关，就把连接异常一同藏进设置。

**冲刺平时可以收起，正在进行时不该到月底才出现。** 不按日期自动搬动模块，也不在跨月时自动隐藏、结束或重置。用户控制展示时机；展示状态与统计数据分开处理。

## Apple 与 Awwwards：借鉴什么

### Apple：先学信息层级和操作方式

Apple 的 Disclosure controls 指南明确建议，把常用控件放在始终可见的位置，把高级细节留到相关时再展示。它还分别说明了不同披露控件的使用方式；不能把某一种按钮的数量建议泛化成“整个页面只能有一个折叠区”。对 LIRA 的应用是：直播状态与近期事件保持可见，配置与完整明细按需打开。[Apple：Disclosure controls](https://developer.apple.com/design/human-interface-guidelines/disclosure-controls)

Apple 的布局指南强调，通过位置、对齐、分组与间距体现重要性，让必要信息有足够空间，并把次要内容放到其他区域或额外视图。对 LIRA 的应用是：最近礼物成为主要阅读区，低频配置退出主阅读顺序，摘要靠近相关内容。[Apple：Layout](https://developer.apple.com/design/human-interface-guidelines/layout?changes=l_1__4&language=objc)

WWDC23 的 Inspector 示例展示了 Keynote 的格式检查器与 Shortcuts 的辅助内容：主任务保持在主体，右侧区域显示相关详情或操作。对 LIRA 的应用是：宽窗口中打开投屏设置时，可以用右侧设置区承接，使用户仍能看到最近礼物。这是交互结构的借鉴，不要求采用 SwiftUI 或改换现有技术。[Apple：Inspectors in SwiftUI](https://developer.apple.com/videos/play/wwdc2023/10161/)

Apple 也把列表和表格用于有共同属性的信息。礼物事件恰好有观众、礼物、数量、时间等重复字段，因此“统一行式列表＋少量图片”值得与当前卡片比较。这里仍应保留 LIRA 已有的礼物图像与身份识别信息。[Apple：Lists and tables](https://developer.apple.com/design/human-interface-guidelines/lists-and-tables?changes=_5)

这些资料支持的是层级、明确反馈和稳定关系。**本报告不建议为了“像苹果”引入大面积透明玻璃、悬浮装饰或重新打造一套操作习惯。** Windows 上的 Electron 仍需遵守本产品的字体、缩放和窗口约束。

### Awwwards：作为视觉探索的补充

本次检索到的相关条目包括 E-Comm 43 的侧边导航与购物车界面，以及 Soul Church 的界面元素集合，其中可见侧栏、导航与自收起 FAQ 等不同交互主题。它们可以作为进一步比较“导航与局部内容如何分开”的素材入口。[Awwwards：Sidebar Menus](https://www.awwwards.com/inspiration/sidebar-menus-e-comm-43-shopify-experience)、[Awwwards：Soul Church 元素页](https://www.awwwards.com/inspiration/slider-soul-church)

但这些并不是直播工作台的使用研究。本次 Awwwards 完整页面浏览发生超时，只取得可检索的条目信息，**没有完成其截图与动效的可靠视觉复核**。因此，不以这些案例证明某种布局更易用，也不把具体视觉效果描述成已经看过。推荐方案主要依据已核实的 Apple 官方资料、LIRA 现状和你的使用习惯。

对这类直播工具，视觉品质应体现在文字清晰、位置稳定、控件一致、色彩克制。展示型网站的大留白、滚动叙事或吸睛动效，不宜直接成为工作台的布局依据。这是针对使用场景的设计判断。

## 四种布局方向的取舍

| 方向 | 能改善什么 | 主要代价 | 判断 |
|---|---|---|---|
| 保持长页面，只缩小间距和卡片 | 很快减少部分高度 | 实时信息与低频设置仍混排 | 可作为短期修补 |
| 所有模块都变成折叠面板 | 实现较直接，页面可以变短 | 用户需要记忆展开状态；展开仍推动后续内容；重要摘要可能一起消失 | 不作为主方案 |
| 所有模块改成双列或瀑布流 | 宽屏能容纳更多内容 | 未按频率分层；长短表单容易留下新空洞；动态排序削弱位置记忆 | 不建议直接采用 |
| 直播概览＋摘要＋按需详情／设置 | 同时处理空间、频率与操作路径 | 需要重新安排入口与显隐状态 | **推荐** |

不建议让新手先拖拽卡片、选择布局模板或配置很多“常用项”。可以先给一个合理默认布局，只保留少量有明确用途的选择，例如是否在概览展示冲刺进度。

## 推荐界面

### 日常直播：把注意力留给最新事件

```text
主功能导航：点歌 / 播放 / 礼物 / 百宝箱

礼物                                      投屏设置    更多设置
状态区：检测状态与异常信息 | 礼物检测开关 | 礼物提示开关

主要区域                               次要区域
最近礼物                  全部记录      今日盲盒摘要
观众 / 礼物与数量 / 时间 / 计入金额      查看盲盒分析
近期事件按稳定顺序排列
                                       冲刺目标：简洁入口

保留原有底部播放器空间
```

宽窗口优先使用“较宽的主区＋较窄的摘要区”。可先以主区约三分之二、侧区约三分之一作为设计起点，但最终按内容宽度决定。侧区只放摘要和短表单，六列表格进入现有分析工作区。

当窗口容不下清晰的两区时，改成单列：状态与近期礼物优先，摘要紧随其后，设置仍通过固定入口访问。若摘要区没有需要展示的内容，就合并为紧凑入口或让主区扩展，不为对称保留空白大卡片。

### 每项内容怎么处理

**最近礼物。** 建议先比较紧凑行式列表与现有卡片：行式列表更便于沿固定位置扫视；卡片更利于强调礼物图像。默认建议以统一行式为主，保留缩略图、身份信息和必要的盲盒结果。完整元数据去详情，不能为紧凑而删除业务含义。显示条数依据窗口可用高度确定，不把示意中的四条当作已经验证的最佳数量。

**今日盲盒。** 概览显示成本、开出价值和观众盈亏等必要信息，不默认展示整张十人榜。明确写“观众盈亏”，避免理解为主播收入。有盲盒需求的人进入完整分析；没有记录时简短说明，不显示一组醒目的零值卡片。直播中有新盲盒数据时更新已有摘要，不自动切换页面或搬动整个布局。

**冲刺。** 未使用时留下“设置／查看冲刺目标”的小入口。用户选择展示后出现已收、目标和还差金额；“调整目标”打开短表单，保存后回到进度。已保存的旧目标不能被擅自清除。关闭进度展示不应停止检测，也不应重置本轮；“重置本轮”保留为独立操作，沿用清楚的确认说明。

**盲盒映射。** 进入“更多设置”后看到“盲盒配置：官方规则自动同步，通常无需修改”。只有需要特殊配置的人才继续进入自定义规则。现有高级 JSON 能力保留，但不把它放在普通直播的首层。官方配置若真的异常，仍需在合适位置给出简短异常提示与入口，不能因其低频而隐瞒问题。

**投屏。** “投屏设置”入口固定、名称明确，进入后先看到“打开画面”和“复制投屏链接”。标题、人数与筛选项按任务组织。把 `-1`、`0` 这种内部编码显示为“全部”“仅显示汇总”等自然语言选项，并完整保留原有取值。链接可以在“查看链接”中检查或手动复制，不必让长地址常年占据概览。

若实际使用表明每场都要复制投屏链接，再将复制按钮提升到概览；不先假设它和收礼查看同样高频。

### 何时还适合向下展开

向下展开适合一个小范围、紧密相关的补充内容，例如高级筛选、少量额外参数、某一项的简短说明。建议展开后仍能保持上下文，收起时留下当前状态或摘要。

独立的大功能、完整明细表、长配置表单适合专门的详情区或设置区。它们不应靠一次大幅向下展开，把用户正在看的其他直播内容推走。

## 三条典型操作路径

### 开播前确认

进入礼物页 → 看状态区 → 必要时打开投屏设置 → 查看画面并复制链接。

用户应能明确知道哪些功能已正常工作、哪些需要自己处理，不应被零值冲刺和映射表单暗示“还没配置完”。异常信息说明下一步；普通界面不要求理解收包、解析命令或 JSON。

### 直播中答谢与查找

最近礼物直接可见 → 需要追溯时点击“全部记录” → 关闭详情后回到原位置。

最新数据可以更新，但当用户正在阅读较早内容时，应避免强行滚回顶部；可在合适位置提示有新记录。用户查看明细时，也不应被普通礼物通知反复打断。此处为交互目标，实施前需核对现有刷新行为，不是对当前页面已发生错误的断言。

### 月底使用冲刺

点击冲刺入口 → 检查已有目标与进度 → 设置或调整目标 → 展示紧凑进度。

这个流程首先管理显示和编辑，不自动调用“重置本轮”。已有进度如何归属沿用现有业务逻辑。只有用户明确选择重置时才执行相应操作；跨月不自动触发。

## 新手友好的具体细节

| 情况 | 建议行为 |
|---|---|
| 没有礼物 | 简短说明“还没有收到礼物，收到后会显示在这里”；状态区解释当前检测情况，不用大插画撑高面板 |
| 检测关闭、未连接、连接正常但暂无数据 | 分别表达，不用同一个“暂无数据”覆盖所有原因 |
| 提示关闭 | 明确只是提示关闭；不要使人误以为历史也被清空或所有礼物处理都停止 |
| 盲盒统计加载失败 | 保留可识别的区域标题；显示具体处理入口，避免永久空白或只有“稍后重试” |
| 打开低频设置 | 有可见的标题和返回入口；不依赖右键、悬停或纯图标猜测 |
| 保存目标或自定义配置 | 在操作附近显示保存中、成功或失败；失败保留输入，避免让用户重填 |
| 复制投屏链接 | 清楚反馈已复制，并提供首次使用说明；复制不等于 OBS 已完成添加 |
| 关闭详情 | 回到原来的阅读位置与触发控件，避免迷失；折叠内容不应留下可误入的隐藏控件 |

字号与按钮大小应先遵循现有桌面设计变量，不另建一套审美系统。建议以正文约 14–16 CSS px、主要点击区域约 32–36 CSS px 起步，最终在实际 Windows 缩放下确认；这些是本报告的原型起点，不是 Apple 官方尺寸要求。重要内容不能只靠颜色区别，小灰字不应承载关键状态。

动效只用于说明局部状态变化，避免整页反复入场、标题悬浮跳动或长表单展开动画。直播时有限的注意力应留给观众与任务。

## 实施顺序与必须保留的业务边界

### 第一阶段：先改变默认信息层级

合并顶部开关的占位，缩短空状态；把冲刺编辑、投屏编辑、盲盒映射从概览移到明确入口后；保留现有历史与盲盒分析入口。先用这些调整验证是否减少无关信息和滚动，不同时重做全部视觉样式。

### 第二阶段：确定主次布局与事件样式

在 Electron 的常用窗口中比较主次两区与单列布局，选择近期事件的合适密度；确认底部播放器展开时仍能操作。宽度不足时主动改变结构，不压缩文字去硬塞两栏。原型里的右侧设置区是建议；现有大型流水和分析工作区应继续按其数据需求使用足够宽度。

### 第三阶段：仅补上与新流程直接有关的交互

完善设置的保存反馈、返回位置、投屏人数的自然语言选项，以及高级配置的说明。若要跨次启动记住“展示冲刺进度”，先明确它是界面偏好还是新的业务状态，再按仓库规则评审，不悄悄复用旧业务键。

开发时尤其注意：

- **不能用 `enableGiftSprint` 控制冲刺面板是否显示。** 当前“礼物检测”写入这个历史命名的键，它参与统计资格和检测状态，并非纯界面偏好。关闭它也不能简单理解成所有礼物采集都停止。[开关绑定](/D:/Work/Live/public/js/admin/settings-form.js:98)、[统计资格](/D:/Work/Live/src/bilibili/gift/projection-service.js:239)
- **隐藏面板、暂停统计、修改目标、重置本轮、清空历史是不同动作。** 当前重置保留流水并归零本轮统计；保持此边界，不因为布局变化触发数据操作。[重置确认](/D:/Work/Live/public/js/admin/settings-form.js:110)、[存储行为](/D:/Work/Live/src/storage/gift-query-store.js:67)
- **不能把投屏链接实时变化描述成全部配置已自动保存。** 现有四项都会更新链接，但只有标题在 `change` 时发起持久化，其余主要作为链接参数；标题保存失败目前没有就地反馈。文案必须对应真实行为。[投屏参数处理](/D:/Work/Live/public/js/admin/settings-blindbox.js:188)
- 布局移动需要保留原有事件绑定、保存时机、DTO、统计口径和页面入口。主区按显示需要缩短列表，不改变实际收礼与历史存储。

以上为落地边界提示。本次只出具报告与示意，没有修改客户端功能，也没有将这些建议写成已接受的规格。

## 怎样验证这次改版是否有效

先验证代表性桌面场景，不要求为了报告跑完整测试套件。窗口选择以实际用户常用尺寸和缩放为准；可用 1280×800 与 1440×900 的内容区域作为初始候选，并补一个并排使用 OBS 时的较窄窗口。明确区分物理分辨率、系统缩放和 CSS 可用尺寸。

| 验证任务 | 建议通过标准（尚未实测） |
|---|---|
| 打开礼物页并判断是否正常 | 用户约 5 秒内能说出当前状态，能区分未连接和暂时无礼物 |
| 找出最近一位送礼者与礼物 | 常用窗口首次打开不必先收起配置或滚过冲刺表单 |
| 日常直播不使用冲刺、映射 | 首层不展示其完整表单；用户仍能找到入口 |
| 找到盲盒配置 | 两次明确点击内到达相应设置区，无需学习手势或纯图标 |
| 开启冲刺进度展示 | 入口位置稳定；操作不会修改检测开关、已有流水或本轮计数 |
| 关闭详情再返回 | 保留原来的上下文与焦点；隐藏内容不会误接收键盘操作 |
| 空记录、很多记录、盲盒失败 | 不产生大块无意义占位，也不因自动出现内容而大幅搬动主任务 |
| 展开底部播放器 | 关键入口可操作，摘要或内容能自然滚动，不被播放器遮挡 |

可先找 3–5 位接近目标画像的使用者完成上述任务，记录寻找时间、误点、是否把可选配置当成必填。这个规模适合发现明显问题，不足以做统计性的提升结论。

成功标准应是“更快看懂、少找入口、不误改”，而不是仅比较首屏控件数量或空白百分比。本次没有宣称减少了多少滚动或提高了多少效率。
