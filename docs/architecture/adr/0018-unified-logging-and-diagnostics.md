# ADR-0018: 统一日志事件与两端诊断入口

## 状态

已采纳（2026-09-14）

2026-11-11 本地代码核验进展：客户端已交付源头降噪、普通/错误日志分流、按容量轮转、跨重启保留、到期清理、敏感信息脱敏及桌面异常采集；服务端日志器已支持脱敏与有界输出。统一事件格式、持久化日写入限额、故障上下文、诊断页面与授权上报按后续阶段推进（本次仅核验本地代码，未复核线上部署环境）。

## 背景

采纳时，客户端虽已有桌面、终端与 AI 日志，但格式、脱敏和保留策略各不相同，且终端与 AI 日志初始化时会覆盖旧记录；当前客户端已补齐分流、轮转与重启保留，详见 [桌面日志参考](../../reference/desktop/main.md#8-日志)。服务端已有 JSON 控制台日志、PM2 与管理操作审计，但运行问题聚合与客户端诊断上报尚未落地。

本决策旨在支持用户导出或提交诊断包，并让管理员统一排查和追踪修复，同时守住安装级 `logs/` 目录、Electron 安全模型、既有租户/凭据/礼物隐私规范以及双端模块化单体边界。

现状证据、数据分类、目录结构、接口职责、风险与验收细则归属 [日志与诊断设计规格](../../../specs/client-server-logging-design.md)；增长测算、精简方案、具体限额及已核实的宝塔/PM2 部署配置见 [专项报告](../../reports/2026-09-14-log-volume-and-signal-report.md)。本 ADR 不重复定义字段与配额。

## 决策内容

1. **格式统一，写入按宿主管理**：采用带版本号的 JSON Lines 格式及统一的事件、严重级别与关联语义；双端各自维护适配器与组合根，不跨仓库 `require` 源文件。优先增强既有日志器，不新增运行时依赖、独立服务或框架。
2. **诊断与审计分离**：`INFO`/`WARN` 写入运行日志（`runtime`），`ERROR`/`FATAL` 仅在错误日志（`errors`）保留一份，界面按时间线合并展示；成功请求以计数汇总为主，访问日志（`access`）仅保留必要异常摘要。独立的 SQLite 诊断库保存受保护的问题摘要与样本；管理员修改的低频问题处理状态在 `admin.db` 独立表中与审计记录同事务提交，避免高频诊断写入与身份库争用锁。`audit_logs` 及其事务与保留策略不按临时诊断缓存随意清理，问题处理状态也非可丢弃索引。
3. **权限先于汇总**：服务端运行诊断首版仅限 `super_admin` 访问；设备上报身份由已认证的服务端边界推导；摘要须经过双端白名单与脱敏处理，私有诊断文件按租户隔离。客户端本地默认可查看与导出，自动摘要须经用户显式开启，原生崩溃转储（dump）不自动上传。
4. **先源头降噪，再限制保留**：正常无变化状态不逐条落盘；保留关键结果、聚合高频活动，并在首次故障时按相关范围转存有界内存线索。重复错误仅记录增量、原因变化与恢复事件。对单条体积、每日写入量、文件数、目录总容量、内存缓冲、索引与导出体积均设上限；常规写入有界异步化，过载时明确标记丢弃；遇到致命错误（`fatal`）时尽力落盘脱敏现场信息再退出，绝不忽略异常继续运行。旧日志保持只读，沿用既有 `Crashpad` 路径；部署侧日志与审计归档各自承担容量上限。
5. **界面围绕问题处置**：客户端在「本地数据」新增查看与导出入口；服务端新增「问题与日志」页面，按稳定异常特征聚合，支持处置、解决与复发追踪，同时保留原有审计入口。近期文件查询设明确扫描上限，不承诺无限全文检索。
6. **部署遵循实际归属**：新应用日志写入可配置的专用目录，保留本机既有 PM2 日志路径，部署侧复用 `logrotate` 并补齐轮转配置；诊断库与租户报告沿用实际的 `admin`/`data_dir` 目录归属。Nginx 原生错误日志须独立验证敏感信息脱敏，不能因访问日志仅记录路径，就误认为所有反向代理日志均已脱敏。

## 备选方案

- **仅把文件夹入口和 PM2 日志挂到 Admin**：开发量小，但缺少页面报错、跨端关联、问题处置及权限/脱敏投影，无法达成目标。
- **把所有日志写入现有 `admin.db`**：查询方便，但会让高频诊断写入与身份、授权及审计争用写入带宽并引入清理风险。
- **立即部署集中式日志集群或第三方错误 SaaS**：功能现成，但增加依赖、运维负担与诊断数据外发边界，当前缺乏引入的容量依据。
- **持续全量上传客户端日志**：虽可丰富排查上下文，但带宽、隐私与滥用成本过高；改为有限错误摘要加用户主动上报。
- **仅做轮转或只保留 `ERROR`**：前者仍产生大量无效磁盘写入，后者丢失故障前关键脉络；改为源头聚合、低频关键结果与有限故障上下文。

## 影响与局限

- **正面影响**：重启前故障得以保留，跨端编号可串联排查，管理员能够清晰区分运行故障与管理操作，同时保持既有平台与目录结构不变。
- **代价**：双端需维护轻量适配器、文件轮转与有界索引、双端样本（fixture）及诊断授权协议。汇总与上下文缓冲需要明确的有界状态与计数语义；日志文件与诊断索引不在同一事务中，必须支持幂等恢复并在界面提示采集延迟。
- **已知局限**：服务完全宕机时同机管理端不可用；过载或突然断电无法保证日志绝对无损；常规细节超出内存窗口后不可恢复；未主动上报的设备无法纳入完整故障率统计；异常聚合仅作排查辅助而非根因证明。受磁盘容量限制无法无限保留审计历史；外部探活、原生转储分析与大型检索平台视后续实际需求再行评估。

## 落地推进

未交付部分按设计规格的 A/B/C 阶段及 `PLANS.md` 编制实施计划；既有容量上限与保留保护不依赖后续问题中心或上传功能。服务端规范文档、协议/OpenAPI、样本、测试及服务端 ADR 随对应服务端实现同步更新；本 ADR 仅代表客户端侧采纳结论，不覆盖服务端规范，也不代表服务端协议或线上部署已上线。
