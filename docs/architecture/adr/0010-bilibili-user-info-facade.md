# ADR-0010: 为 Bilibili 用户信息引入后端门面

## 状态

已采纳

## 背景

LIRA 此前在 B 站弹幕、醒目留言（SC）、历史消息、在线榜、粉丝牌轮询及小游戏头像查询等多处重复读取用户信息。`IdentityCache` 既承担字段合并，又维护最近用户与在线名单；部分轮询器和小游戏代码直接访问缓存或调用 `BilibiliApiClient.fetchUserProfile()`。此外，`BilibiliDanmakuClient` 把 `onMessage() === true` 当作头像拉取的隐式触发信号，使业务回调返回值意外耦合了网络请求。

现有实现与测试还约束：当前房间身份必须绑定主播 UID；未提供的字段不得清空已有缓存；只有经过验证的当前房间缺失状态才能清除旧的别家身份；头像仅能通过可信 B 站 URL 校验及本地代理返回。一次性重写解析器或缓存会放大回归影响面，也不符合 LIRA 的模块化单体与兼容原则。

## 决策

增量引入 `UserInfoService` 门面，先作为 B 站领域内的统一入口，再由运行时通过专用门面或端口注入跨领域调用方：

- **解析器与轮询器边界**：消息解析器仅产出 `IdentityHint` 与消息载荷（`DANMU_MSG` 与 SC 共享内部 `user` 结构，文本、金额与礼物字段留在各自载荷中），不触碰缓存、网络或业务通知；领域内部可装配统一的 `BilibiliMessageEvent`，对外继续由兼容适配器保持既有消息、HTTP/WS 与前端事件格式。各轮询器只请求各自负责的接口（历史消息/在线榜/粉丝榜），并通过注入的接收器提交身份线索，不得直接访问缓存、资料提供方或头像代理。
- **服务职责与生命周期入口**：`UserInfoService` 提供 `peek`、`ingestHint`、`ensure`、`listRecent`、`listOnline`、在线快照更新、订阅通知与房间作用域管理，并暴露 `setRoom()`、`beginRoomRun()`、幂等的 `endRoomRun()` 与 `dispose()` 生命周期入口。
- **独占合并策略**：`UserInfoService` 是唯一的字段合并策略归属模块；迁移期内 `IdentityCache` 退化为底层存储与索引兼容原语，仅保存服务合并后的最终状态。旧方法签名可暂留兼容，但内部只能委托给 `UserInfoService` 或执行精确投影读取，不得再自行裁决优先级、新鲜度、已确认缺失或来源依据，也不允许新生产方或调用方绕过门面访问。
- **全局资料与房间身份分离**：`name`/`avatarUrl` 作为 UID 全局资料；大航海（`guard`）与粉丝牌（`fansMedal`）作为 `{roomId, ownerUid}` 房间身份，采用“有值 / 未知 / 已确认不存在（verified absence）”三态。非空粉丝牌必须保存并校验 `targetUid`（不能只存 `roomId`），已确认缺失状态不伪造 `targetUid`。代次（`generation`）与运行令牌（`runToken`）仅用于内部作用域校验、异步写入资格判断与诊断，不进入 `UserInfoSnapshot`；用户资料不缓存弹幕文本、SC 内容、金额或礼物数量。
- **字段投影与参数校验**：`peek`、`listRecent`、`listOnline` 与 `subscribe` 支持 `fields` 投影——永远返回 `uid`，可选字段仅限 `name`、`avatarUrl`、`guard`、`fansMedal`（未传 `fields` 的订阅等同于四字段全量投影，`uid` 不计入 `changedFields`）。参数校验先于过期检查：非数组、非字符串元素、未知字段以及对 `ensure` 请求房间字段均抛出 `TypeError`，重复字段去重；投影绝不泄露 `updatedAt`、来源依据或生命周期令牌。未知线索属性予以忽略，未知来源记录诊断后抛出 `TypeError`。
- **过期房间上下文拦截**：显式传入非当前 `roomId` 时，`peek`/`ensure` 直接返回 `null`、`list*` 返回 `[]`、`subscribe` 返回空退订函数且不通知，且 `ensure` 不发起上游查询。匹配当前房间发起的 `ensure` 会捕获当前房间代次，发生 A→B→A 切房后旧调用方固定收到 `null`，但拉回的全局资料结果仍可合入全局状态。
- **字段合并顺序与历史排序**：按字段独立合并——昵称先质量后新鲜度，头像先合法性后新鲜度，来源仅在时间与质量相同时兜底裁决；房间字段的消息权威权重为 `danmaku/superchat/gift = 30`，固定按“已验证状态 → 未过期来源权威 → 新鲜度”比较，已确认缺失沿用同一比较器。`observedAt` 统一取服务接收线索的时刻；历史消息轮询必须串行执行，同批按从旧到新稳定排序并去重后再写入，避免旧记录拿到更新的观测时间。
- **房间代次与共享 `runToken`**：房间代次（`generation`）仅在 `{roomId, ownerUid}` 变化时递增。`setRoom()` 清除旧房间身份后，未绑定特定 `roomId` 的通用订阅立即收到受影响 UID 的新作用域房间投影失效通知；显式房间订阅则先失效且不收事件。`beginRoomRun()` 要求存在有效房间作用域，每次调用均失效旧运行周期、清空在线快照并签发新 `runToken`；组合根在整个房间运行时单次启动或协调重连时仅调用一次（重连顺序为 `end(old) → begin() → start all`），历史/在线榜/粉丝榜轮询器共用该上下文。单个轮询器重启复用既有上下文，不调用 `begin`/`end`，依靠自身局部代次与中止信号在 `await` 后及写入接收器前阻断停止后的回写。带房间作用域的 `ingestHint()` 与 `replaceOnlineSnapshot()` 必须同时匹配 `{roomId, ownerUid}`、代次与 `runToken`，失效上下文的混合线索整条拒绝；无房间上下文的全局资料结果仅校验服务生命周期令牌。
- **并发合并与短期缓存**：资料查询按 `profile:${uid}` 执行并发请求合并，上游失败做短期否定缓存（30 秒，到期后允许重试）。第一阶段仅使用内存缓存并保持既有 10 分钟 TTL，不新增持久化、HTTP、IPC 或 preload 约定。
- **显式头像拉取与代理独立**：业务需要头像时显式调用 `ensure()`，迁移完成后移除 `onMessage() === true` 与 `resolveDanmakuAvatar()` 隐式路径；头像代理继续独立负责 URL 校验与图片转发，不参与身份合并。

详细数据模型、合并比较器、迁移阶段与验收细则归属 [Bilibili 用户信息模块化设计](../../../specs/bilibili-user-info-service_design.md)。本 ADR 与规格均已采纳，但不授权改动其中明确保持兼容的 HTTP、WebSocket、IPC、数据库、preload 或前端事件约定。

## 影响

### 正面影响

- 用户信息合并规则集中收口，完整昵称、当前房间粉丝牌与头像来源可通过字段级测试锁定。
- 轮询器、小游戏与渲染进程不再依赖 `IdentityCache` 或 B 站资料接口的内部实现。
- 并发请求合并、房间代次防护校验（fence）与房间运行时级共享 `runToken` 显著降低重复请求、旧房间串写、同房重连旧请求回写及多轮询器互相失效的风险。
- 既有 HTTP、WebSocket、IPC、数据库与头像代理接口保持兼容。

### 代价

- 迁移过渡期内 `UserInfoService`、旧缓存接口与兼容适配器需要并存。
- 迁移期须防止旧 `IdentityCache` 再次执行字段合并，适配层需明确区分“已合并状态写入”与遗留合并入口。
- 组合根需显式注入用户信息门面与轮询器接收器，装配参数略有增加。
- `UserInfoSnapshot` 的三态语义、字段投影与订阅 `changedFields` 需要补充专项单元测试，不能仅依赖旧字段断言。

### 中性影响

- 不新增进程、端口、数据库、第三方依赖或 Electron 权限。
- 历史身份落盘与持久化头像不在本 ADR 范围内，后续如有需要另行决策。

## 备选方案

**直接重写 `IdentityCache` 与全部解析器**

- 否决：同时改动协议解析、缓存合并、轮询生命周期与事件格式会导致回归影响面过大；先建立门面锁住边界再渐进迁移风险更可控。

**让各调用方直接调用 `BilibiliApiClient`**

- 否决：会导致重复请求、泄露鉴权与上游实现细节，且违反跨领域经由显式门面/端口交互的模块化规范。

**将用户资料持久化至 SQLite**

- 否决：当前诉求为统一读取与短期内存复用，不需要引入表结构、迁移、过期清理及隐私留存策略。

**为渲染进程新增 `UserInfoService` IPC**

- 否决：现有 HTTP/WS 事件已可承载兼容数据，现阶段扩大 preload 接口范围没有边界收益。

**为每个轮询器分配独立 `runToken`**

- 否决（第一阶段）：当前核心诉求是隔离整个房间运行时协调重连前后的旧写入；独立令牌会增加上下文与组合判断复杂度。单轮询器重启复用共享房间 `runToken`，靠自身局部代次与中止状态阻断停止后回写；若未来确实需要单轮询器跨重启保留并发请求，再另立决策扩展。

## 安全与故障边界

- 资料请求沿用 B 站 API 客户端的鉴权边界，快照与事件不包含 Cookie、令牌或完整上游响应。
- 头像仅保存归一化后的可信 HTTPS URL，图片继续经 `/api/bilibili/avatar` 代理输出。
- 上游查询失败使用 30 秒否定缓存抑制雪崩重试；单个订阅者抛错不得阻塞其他订阅者或缓存合并。
- 切房与同房协调重连通过上文决策中的房间代次（`generation`）与共享 `runToken` 防护校验杜绝旧异步结果串写；`endRoomRun()` 仅在整组生产方停止或协调重连时原子失效旧 `runToken` 并清空在线快照（同房重连仍保留 TTL 内的房间/最近状态直至新轮询成功）。房间运行时停止由组合根清理定时器与写入路径；显式房间订阅随切房代次失效，通用资料订阅持续有效直至主动退订或 `dispose()`。

## 回滚策略

实施阶段若专项测试或公共接口回归失败，保留既有 `IdentityCache` 与旧消息字段，通过关闭服务适配层回退至原路径，不得采用大范围回滚重置或删除共享数据。仅在所有直接调用方迁移完成且测试通过后，再移除旧头像触发器与兼容入口。
