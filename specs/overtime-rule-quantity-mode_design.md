# Feature: 加班礼物数量计算方式

## Requirements (EARS Format)

- 当用户编辑一条加班礼物规则时，系统应允许选择“按连击组”或“按具体数量”。
- 当规则选择“按连击组”时，同一次连击最终封账为 50、100 或 500 个礼物都只执行一次规则。
- 当规则选择“按具体数量”时，普通礼物数量和大航海购买月数均应作为规则执行次数。
- 当旧规则没有数量计算字段时，系统应按“按连击组”读取，避免升级后时间突然倍增。
- 当新建舰长、提督或总督规则时，管理端应默认选择“按具体数量”。
- 当同一最终事件被重复投递时，系统仍应只生成一条结算，不能重复计算数量。
- 原始礼物数量继续接受正安全整数并完整持久化，不因自动结算容量而裁剪付费账本。随机 `item` 模式的自动处理范围为 1–100,000 次；这是本机支持容量，不是 B 站平台数量声明。超限在任何抽取和倒计时修改前以 `OVERTIME_QUANTITY_LIMIT` 失败，保持完整数量、金额和 `pending` 记录，不写部分结果或成功状态。固定模式及 `group` 模式沿用现有有界计算。
- 超限使用既有失败记录和最高 30 秒退避重试，每次只检查边界；界面明确显示数量超限且尚未结算的笔数。不得自动改成按组计算、拆单或少算。任何后续处置必须明确调整支持容量或由用户修改规则，只有完整执行后才能完成结算。

## Architecture

### Frontend

- 每条规则增加数量计算单选项，并把 `quantityMode: group | item` 随规则保存。
- 规则摘要显示当前数量计算方式；结算流水显示实际执行次数。
- 客户端只接受固定枚举值，所有礼物名称继续通过 `textContent` 输出。

### Backend

- `validateRules` 服务端校验 `quantityMode`，缺失时兼容为 `group`。
- 数量计算方式随规则一起存入现有 `outcomes_json`，无需数据库迁移。
- 固定规则按执行次数重复应用；时间盲盒在 `item` 模式下独立抽取对应次数。
- 结算仍以 `gift_event_id` 为唯一键，保证重复包和恢复扫描幂等。

### Security

- 规则接口继续使用现有 session token 鉴权和请求体大小限制。
- 服务端不信任前端枚举值，只接受 `group` 与 `item`。
- 数据库写入继续使用参数化语句；响应不增加敏感字段。
- 页面使用原生控件和 `textContent`，不引入远程 HTML 或脚本。

## Acceptance Criteria

- 旧规则与缺少字段的 API 输入默认为按连击组。
- `group` 模式下 `×10` 只执行一次；`item` 模式下执行十次。
- 大航海 3、6、12 个月在 `item` 模式下分别执行 3、6、12 次。
- 时间盲盒按具体数量独立抽取，并持久化本次全部抽取索引。
- 100,000 次完整抽取、索引保留及重放幂等通过；100,001 和最大安全整数在首次、重放、重启恢复时均零抽取、零时间/revision 变化，原数量金额保留，正常下一笔可继续结算。超限笔数在现有待结算位置明确提示。验证：`test/overtime-quantity-boundary.test.js`。
- 非法 `quantityMode` 返回 400，不能进入数据库。
- `npm run check` 与 `npm test` 通过。
