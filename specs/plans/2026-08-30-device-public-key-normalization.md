# Device Public-Key Normalization Implementation Plan

> Status: Complete

> **For agentic workers:** Execute the checked steps in order. Do not commit,
> deploy, or use real activation credentials.

**Goal:** Make first-device activation signatures verify when Electron submits a
Node-generated SPKI PEM public key with its normal trailing newline.

**Architecture:** Protocol-v2 canonicalization remains byte-compatible for
already-normalized keys. Both the desktop and LIRA Server canonical builders
will hash `String(publicKeyPem || '').trim()`, matching the server HTTP boundary
that already trims the submitted PEM. No endpoint, field, algorithm, protocol
version, persisted format, or authorization policy changes.

**Tech Stack:** Node.js 24 CommonJS, Electron 43, Express 5, `node:test`, JSON
OpenAPI/fixture contracts.

## Global Constraints

- Preserve protocol version 2, SHA-256 signatures, supported SPKI algorithms,
  fingerprint requirements, activation-code one-time semantics, and all HTTP
  response/error shapes.
- Never log or persist a plaintext activation code, password, private key,
  signature, or raw hardware identifier.
- Keep integrity enforcement independent from activation-proof verification.
- Touch only the canonical public-key normalization path, directly related
  tests, and required normative documentation.
- Do not commit, publish, deploy, add dependencies, or modify runtime data.

---

## Goal

Normalize the SPKI PEM identically on both sides before calculating
`publicKeySha256`, so the signature generated by the desktop verifies against
the payload reconstructed by the server.

## Non-goals

- No TLS/Nginx deployment work or change to `LIRA_LICENSE_API_BASE`.
- No relaxation of `DEVICE_REQUIRE_VERIFIED_INTEGRITY` or build allowlists.
- No code-signing, remote-attestation, key-storage, fingerprint, or UI redesign.
- No activation-code regeneration, consumption, or database mutation.

## Current Behavior

- Node's PEM export ends with `\n`.
- `src/electron/license/license-protocol.js` hashes the public key verbatim.
- `D:/Work/lira-server/src/routes/device.js` trims the submitted public key
  before `D:/Work/lira-server/src/lib/device-license.js` rebuilds the canonical
  payload.
- A synthetic P-256 reproduction proves the payloads differ and the server
  rejects the otherwise valid signature with `ACTIVATION_PROOF_INVALID`.
- Existing golden vectors use `public-key`/`TEST_PUBLIC_KEY_FIXTURE` without
  surrounding whitespace, so they do not cover the production PEM shape.

## Compatibility Constraints

- A public key with no surrounding whitespace must produce the existing golden
  canonical string unchanged.
- A public key with surrounding CR/LF or spaces must produce the same
  `publicKeySha256` as its trimmed PEM.
- The server must continue parsing and validating the trimmed SPKI PEM before
  entering the activation domain flow.
- Existing keys, identities, codes, and database records require no migration.

## Proposed Changes

- Desktop: add one small `normalizePublicKeyPem(value)` protocol helper and use
  it only for activation `publicKeySha256` canonicalization.
- Server: add the equivalent helper in the canonical protocol module and use it
  for activation `publicKeySha256` canonicalization.
- Tests: generate a real P-256 PEM, assert it ends with a newline, and assert
  that canonicalization is invariant to surrounding whitespace. Verify a
  client-style signature against the server canonical payload.
- Contract: state that the SPKI PEM is trimmed before hashing; update
  `REQ-AUTH-001`, `AC-AUTH-001`, OpenAPI, and the shared fixture input so the
  machine-readable vector contains a trailing newline without changing the
  expected canonical payload.
