# 持续只读审计

Status: Completed

## Goal

针对当前 LIRA 维护中实现持续寻找有证据的安全、正确性、资源消耗、调用和可维护性问题。输出可复用且随证据更新的提示词、按优先级排序的发现和覆盖记录。用户于 2026-11-05 明确选择“只审计，形成按优先级排序的报告和修复建议”。

方法已发展到第八批：除身份、事务、草稿、解析预算、混合数据表示、暖缓存与资源恢复外，补齐菜单所有关闭路径、批量播放计数、真实 HTTP 背压/中止和 SSE 断流期间的持久化恢复。每批新增事实、反证或有效覆盖，不追求固定缺陷数量；只有已检查的调用链计入覆盖。

用户补充要求避免过度审计。本次基线在第八批收束，不自动追加第九批；已有报告、优先级、修复方向和可复用提示词构成交付。后续以相关代码变化、实际问题或具体高影响线索触发增量续审，先选择能改变工程决策的问题。未知范围不等于必须立即补全；被平台中止的检查保持未验证，不改写或换手重试。

## Scope And Non-goals

- 主范围为 `D:\Work\Live`；按调用关系检查与 LIRA Server 的契约，不能据此宣称已完成服务器全仓审计。
- 不改产品代码、既有测试、配置或契约，不提交、建分支、发布，不恢复历史暂停的整改。
- 不访问真实用户数据、生产账户或服务，不操作用户运行中的 Electron。隔离复现和原始证据仅放仓库根 `tmp/continuous-audit-2026-11-05/`。
- 不以缺陷数量、代码短或“像人写的”为目标；必要的安全、事务、兼容和生命周期边界不能因简化而被建议删除。

## Milestones And Verification

1. 建立基线与历史去重，复用已有方法并缩小本轮具体问题；记录检查路径及来源，不把文件清单算作人工审阅。
2. 并行检查风险边界；每个候选追踪入口、owner、消费者、现有测试，检查反证。性能结论附规模、次数或开销证据。
3. 用已有聚焦测试或最小合成复现补证。运行前检查副作用；不自动运行全套、不向真实上游发送请求。复现失败时记录原因而非降低断言。
4. 主代理复核、去重并按影响排序，更新提示词和下一批优先路径。每批进步可为新发现、新覆盖、反证或验证，不能机械重复或强求新增缺陷。
5. 文档更新后运行 `npm run verify:docs`、`git diff --check`，审阅文档 diff 和 `git status --short`，确认没有产品改动及秘密进入产物。

## Failure Handling

证据不足保留为待验证，不补写不存在的复现结果。某一路径受限时继续其它独立审计，并准确记录边界。若需撤销产物，仅撤销本任务自己的文档编辑，不做破坏性 Git 操作。

## Done When

提示词、累计报告、覆盖与续审条件能支持后续增量审计；每批发现有可检查证据和最小建议，文档验证通过。本次完成指基线审计交付，不等于产品修复、项目零缺陷或全仓验收。继续检查需要具体风险依据，不能以消灭所有未知为完成条件。
