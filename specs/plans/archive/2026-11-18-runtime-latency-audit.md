# 桌面与服务端秒级处理排查

**Status:** Completed

## 目标与判断方法

从日常入口查找可以在本地消除的秒级等待。以当前工作树（包括已有修改）为基线。把首次与重复操作、同步阻塞与后台总时长分开计量。用同一输入对照输出和用时，记录规模、测量边界与复测命令。

## 分工与检查点

- 从 Electron 启动、资源库、场景投影、本地 HTTP 与 WebSocket 的消费者，核对是否存在重复 IO、计算和等待。检查已有缓存的校验与失效边界。
- 从本地存储及直播、粉丝、歌曲业务模块定位随记录数放大的处理。使用临时 SQLite 或合成事件复现，检查排序、重复键、隔离和事务边界。
- 从前端管理、播放、歌词和叠加层的交互入口检查重复渲染与串行工作，按实际运行环境验证改变的行为。
- 在配套服务的请求和事件链路用隔离数据核对查询与处理成本，保留租户、数据完整性和订阅边界。

## 交付和验证

只在审计证明的热点修改所属模块。测试随具体行为归属，复跑既有用例，覆盖实现改变引入的边界。技术参考对齐发生变化的事实。用户操作发生变化时同步指南。最后运行 `npm run verify:docs`、两仓各自的 `git diff --check`，对照工作树确认改动。结项记录每项结果及仍需实际环境计量的部分。

## 范围与回退

基准使用仓库 `tmp/` 中的独立合成数据。真实账号、生产服务与运行中的桌面不参与基准。保留采样窗口、限流、重连、协议与持久化语义。若优化无法保持结果，停止该项修改，只撤回本次负责的改动，保留其他进行中的工作。

## 桌面资源实测

Windows、Node 24.21.0，当前许可的 66 个启动文件按正式 v2 目录组成 20 包。使用合成内容和内存 CDN，每轮由 `serveResourceAsset` 执行首个字体 GET，核对返回字节。每一对冷、暖运行共享独立缓存，三对分别重建目录。

| 从初始化到首个字体 GET 返回 | 修改前 | 修改后 |
| --- | --- | --- |
| 冷缓存，三次 | 2,060 / 2,055 / 2,061 ms | 47 / 16 / 27 ms |
| 暖缓存，三次 | 57 / 55 / 52 ms | 41 / 56 / 49 ms |

冷缓存各轮全程各发 21 个请求，包含 1 个清单和 20 个包，对象共 34,790 字节。全量准备仍用约 2.1 秒，耗时来自每秒 8 次的下载限速。暖缓存仅取清单。现在已等待的读取方在本机校验命中或当前包提交时收到通知。资源测试 15 项通过，包括新摘要、坏包、离线与关闭。隔离 ASAR Electron 实测全部共享字体、8K 地图及离线重开通过。复测入口为 `node tmp/runtime-latency-audit/cdn-first-asset.cjs`。

随后用仓库正式素材和同一套本地 CDN 替身做三对交错复测。冷启动各取 102,222,033 字节，首个字体从 2,137–2,156 ms 降到 50–56 ms。暖启动各取一次清单，首个字体从 235–260 ms 降到 141–155 ms。真实素材冷启动全量准备两版均约 2.1–2.2 秒。复测命令为 `node tmp/runtime-latency-audit/cdn-real-assets.cjs`，修改前模块取自本轮开始时相同的 Git 版本。

## 桌面旧日志迁移

五次独立进程的同步维护中位数。接近 1 MiB 的 10,180 条旧终端错误从 8,566 ms 降到 48 ms，4,922 条旧 AI 错误从 2,866 ms 降到 86 ms，200 条普通记录从 3.52 ms 降到 2.36 ms。终端样本的目标写入从 10,180 次降到 1 次。六种启动样本的输出目录摘要前后一致，44 项日志与脱敏回归通过。启动后桌面与 AI 单条日志的 P95 分别为 0.77 ms、0.77 ms。

保留边界和短写恢复由 `src/shared/log-size-limit.js` 与 `src/electron/log-maintenance.js` 负责。Windows 持续锁住已满的活动日志时，原有轮转顺序会在两次失败后淘汰两份旧归档。旧版与本版均复现，细节在桌面日志参考。该问题已在[后续复核](2026-11-18-runtime-latency-followup.md)中修复，并用 Windows 文件锁验证。测试入口为 `node --test test/desktop/log-maintenance.test.js test/shared/log-size-limit.test.js`。

## 直播指令、AI 准入和网易云歌单

Node 24.21.0，每组预热一次、计时三次取中位数。自定义指令在配置变化时编译 30 条规范化关键词，30,000 条弹幕的总计时从 1,267 ms 降到 81 ms，两版均命中 7,500 条。AI 准入复用配置提交时的快照，继续按账号会话代次检查。对 20 个角色包、30,000 条普通弹幕，完整配置读取从 60,001 次降到 1 次，API 模式的批处理从 1,134 ms 降到 49 ms，豆包账号模式从 1,134 ms 降到 88 ms。这些耗时仅覆盖准入判断。

网易云歌单的上游替身对每次请求施加 40 ms 延迟。2,500 首完整内嵌曲目检查末尾成员时，从 27 请求、1,261 ms 降到 1 请求、46 ms。另一种只提供 ID 的歌单仍须分批读取详情，去掉相同详情的二次封面请求后，从 51 请求、2,387 ms 降到 26 请求、1,216 ms。验证了完整/截断列表、索引顺序和图片回退。涉及 `src/music/providers/netease-provider.js`、`src/ai/ai-assistant-service.js`、`src/bilibili/custom-reply-service.js`，该组 172 项直接和相邻用例通过。

随后单独从播放器内容加载入口复测完整歌单。每次上游请求延迟 40 ms，各场景三轮。2,500 个不同 ID 的歌单使用相同的 26 次请求、578,177 字节响应，从 1,235 ms 降到 670 ms。2,500 个位置中 1,200 个 ID 唯一时，从 26 次请求、1,233 ms 降到 13 次、338 ms。每个普通歌单最多并读两批，同一 Provider 的全部歌单读取共享六个名额，完成后按完整索引回放重复位置。主档只提供内嵌列表和完整封面时两版各发一次请求，中位 60、69 ms。

缺失一首详情的故障从 1,213 ms 降到 93 ms，发现失败后追加请求由 24 次降到 0 次。9 路同时打开 513 首的歌单时，总请求数均为 63，峰值并发从 9 降为 6，替身延迟 4 ms 时所有请求完成从 114 ms 升到 167 ms。排队时切换账号，旧读取向新账号发出的请求为 0。39 项定向检查通过。隔离基准和原始数据在 `tmp/netease-playlist-open-20261118-r1/`。

## 全民 K 歌按歌名查找歌词

| 按歌名查找 | 修改前中位 | 修改后中位 | 每次解密文件数，前 → 后 |

## 配套服务的设备续页与礼物统计

Windows，服务端仓库 Node 24.15.0，5 个隔离租户。主租户 225 天内有 150,000 笔礼物，80 种礼物、10,000 个观众名，盲盒占 25%。两个版本保留相同的并行改动，在独立进程各跑五轮。统计时间含服务入口、查询工作线程、SQLite 读取及结果交付。

| 路径 | 修改前中位 | 第一轮优化后中位（范围） |

旧设备用现有终态事件索引续页，首个完整性检查从 614 ms 降到 200 ms。两版 1,000 个事件 ID 和顺序完全一致。统计在一个租户的读事务内共用相同财务事实的贡献，并逐笔核对事件 ID 与观众名。同一上海月内如涉及保留期，则以日拆分。对照检查涵盖总额、明细可用数、排行、时间序列与礼物构成。单独把 150,000 笔的单价频繁改动，直接计量只读 SQLite 和计算器，三轮中位从 3,612 ms 降到 3,201 ms。
