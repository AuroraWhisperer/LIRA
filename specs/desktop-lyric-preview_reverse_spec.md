# 桌面歌词预览链路逆向说明

## 分析范围

本说明只覆盖“播放/全民 K 歌歌词数据 → 服务端实时状态 → 管理页桌面歌词预览”。证据来自：

- `public/js/playback/services/lyric-service.js`：在线播放歌词加载及当前行发布。
- `src/music/wesing-capture.js`：全民 K 歌完整歌词和当前行计算。
- `src/music/lyric-state.js`、`src/server.js`：当前行状态规范化、快照及 WebSocket 广播。
- `public/js/admin/state.js`、`public/js/admin/desktop-lyric-preview.js`：管理页状态接收与单行预览。

## 观察到的数据流

1. 在线播放端把完整歌词保存在 `track.lyrics.lines`；全民 K 歌捕获端把完整歌词保存在闭包变量 `lyrics`。
2. 两条链路都只调用 `findCurrentLyricLine()`，把当前行的文字、翻译和逐字时间发送为 `lyric-state`。
3. 当播放时间早于第一条歌词时间戳时，当前行是 `null`，规范化后的 `lineText` 和 `words` 均为空。
4. 管理页预览只创建一个 `LyricWordRenderer`，没有完整歌词列表的数据或 DOM，因此 `status === 'ready'` 且当前行为空时只能显示“前奏中”。
5. WebSocket 单帧上限为 256 KB；完整歌词不能附在约 180ms 一次的高频当前行状态中重复广播。

## 观察到的需求（EARS）

- 当一首歌曲的歌词加载完成时，系统应向管理页提供经过限制的完整歌词时间轴。
- 当播放位置变化时，系统应继续用轻量当前行状态驱动逐字高亮，不应重复发送整首歌词。
- 当播放时间早于第一句或处于长间奏时，系统应保留完整歌词列表，并在下一句临近时显示倒计时。
- 当用户手动滚动歌词时，系统应允许查看任意歌词行，短时间内不应强制拉回当前行。
- 当歌词内容来自浏览器时，系统应限制条数、字段长度和总字符数，并使用文本节点输出。

## 不确定性

- 制作人、出品和营销信息没有独立字段；现有 QQ/网易云/QRC 数据把这些信息作为带时间戳的歌词行提供。本次修复完整展示这些行，不猜测或合成缺失的制作名单。
- 紧凑的独立桌面歌词窗口当前明确设计为单行窗口；用户截图指向管理页实时预览，因此本次不改变独立窗口尺寸和交互。
